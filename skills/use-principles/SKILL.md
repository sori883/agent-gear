# 開発作業の運用ルール

開発ルールと原則の正本は、利用先プロジェクトのOKF bundleに置く。このスキルは文書を読むタイミングと作業の進め方を定める。ルールや原則の本文をここへ複製しない。

同梱する23原則は `type: principle`、`governance: context` とし、作業の目的や制約と照らして判断の指針にする。この開発用bundleに追加するルールは `type: rule`、`governance: constraint` を明示し、具体的に守る行動・禁止事項・承認条件を記す。これは配布文書の作成方針であり、読み取る文書の扱いは個々の `governance` で確認する。

## 適用範囲と権限

- 調査、設計、実装、不具合修正、性能改善、レビュー、開発文書・スキルの編集に適用する。簡単な変更に大規模な工程を追加しない。
- ユーザーの依頼範囲、現在の指示、既に得た承認、利用環境の権限に従う。「コミットしない」「worktreeを使わない」「読み取りだけ」などの指定を、原則や手順で上書きしない。
- 依頼範囲内の可逆的な作業は進め、同じ承認を繰り返し求めない。方針や好みなど、調査では決められない事項だけを確認する。
- 外部へのメッセージ送信、Issue・PRの操作、push・マージ・デプロイ、削除などは、その操作に必要な依頼・承認がある範囲で行う。このスキルの適用は操作権限を増やさない。
- 「続けて」「寝るので進めて」は作業継続の指示として扱う。中断や引き継ぎを依頼された場合は[checkpoint-safely](../checkpoint-safely/SKILL.md)を使う。

## 1. 適用する原則を読む

1. [OKF Agent Memory](../okf-agent-memory/SKILL.md)の検索・参照手順とCLIの準備を確認する。作業ディレクトリは利用先プロジェクトのルートに保つ。
2. 開発作業の開始時に、対象bundleを `search --type rule --all` と `search --type principle --all` で検索する。検索語やパスで候補を狭めず、それぞれ全件の `description` を取得する。
3. 今回の依頼、成果物、変更対象、作業の段階を各 `description` に照らし合わせ、合致する文書の `concept_id` を選ぶ。適用するか判断しづらい文書も選び、明らかに対象外の文書は本文を取得しない。個別の適用条件や固定IDの対応表をスキルに持たない。
4. 選んだ文書を `show` で読み、詳細な適用条件、例外、`governance` を確認して扱いを決める。`context` は判断の背景として参照し、`constraint` は条件に該当する制約を守る。descriptionだけで読了・適用済みと扱わない。
5. 対象領域を初めて変更するときは、実際のファイルパスごとに `search --for-path ... --all` を実行する。この確認ではtypeを絞らず、ほかの種類に付いた制約も取得する。`hold`、`constraint`、`context` の扱いはOKFの手順に従う。
6. 作業の段階や対象範囲が変わったら、descriptionから適用する文書を選び直す。既に読んだ同じ本文の再取得は、内容が変わった場合や再確認が必要な場合に行う。

利用先のルートに `skills/` と `.space/babel/` を配置した場合は、ルートから次のように取得する。別の配置先では、OKF Agent Memoryのスキル配置先と指定bundleに合わせる。

```sh
bun skills/okf-agent-memory/scripts/okf.ts search --type rule .space/babel --all --json
bun skills/okf-agent-memory/scripts/okf.ts search --type principle .space/babel --all --json
# descriptionから選んだconcept_idを指定して本文を読む
bun skills/okf-agent-memory/scripts/okf.ts show '<選んだconcept_id>' .space/babel --json
bun skills/okf-agent-memory/scripts/okf.ts search --for-path 'skills/use-principles/SKILL.md' .space/babel --all --json
```

`rule` が0件でも、検索が正常終了していればルール未登録として原則の確認へ進む。必要な原則を取得できなければ、対象bundleと配布物の配置を確認して復旧する。取得したことにせず、適用判断に依存する変更を待つ間は、依存しない調査を進める。`--all` の出力が利用するツールで省略された場合は、出力をファイルに保存して分割して読み、未確認のdescriptionを残さない。

## 2. 作業の目的と手順を決める

依頼が求める成果物、変更してよい範囲、完了を示す証拠を短く定める。複数段階の作業では、作業順序、担当範囲、検証の区切り、反復を道具で処理できるかを先に整理する。省略する工程は、今回不要な理由を示す。

| 作業 | 進め方 |
| --- | --- |
| 仕組み・設計理由の調査 | 現在のコード・仕様・変更履歴・一次資料から説明する。事実、推論、未確認事項を分ける。調査だけの依頼から修正へ広げない |
| 設計・新機能 | 利用者の使い方、データの形、型、モジュールの責務を先に決める。関数境界を越える変更では呼び出し側も確認する。未知の選択肢は小さく比較する |
| 不具合修正 | 実際の利用経路で再現し、原因を特定する。安価な局所テストがある場合は失敗を確認してから修正し、同じ経路で検証する |
| 性能改善 | 基準値と測定条件を記録し、計測した原因へ変更を加え、同じ条件で前後比較する。継続改善では仮説と採否を残す |
| リファクタリング・移行 | 保つ振る舞い、移行先、互換性の条件を定め、呼び出し元を調べて検証可能な単位で進める |
| UI・CLIの変更 | 利用可能な操作・実行手段で実物を確認する。見た目の同等性が要件なら、同じ条件の画面や出力を比較する |
| 文書・スキルの変更 | 読み手、適用条件、既存構造、参照先を確認して編集する。形式検証と実際の判断・動作の確認を区別する |
| レビュー | 差分と証拠を自分で確認する。自動レビューの指摘も再現性と影響で判断し、修正・理由付きの見送り・確認事項へ分ける |
| PRの状態確認・公開 | 求められた操作を明確にし、CI・競合・レビューの現状を確認する。CI成功だけでマージの安全性を推定しない。依頼された公開範囲だけを実施する |
| 再開・長期作業 | 保存された状態と実際の差分・稼働処理を照合して再開する。長期作業では検証の区切りと判断記録を維持する |

利用先で利用可能な調査・設計・計画・型設計などの既存スキルが適合する場合は、その作業の手順を使う。用途と権限が合うものだけを選び、未導入のツール・モデル・スキルを必須にしない。agent-gearの開発用 `.agents/skills/` を利用先にも存在するものとして参照しない。

観測すれば分かる振る舞い・性能・レイアウトの判断は、実行や小さな試作で確かめる。読み取りだけの依頼では既存の証拠から回答する。既存の手順が合わない場合も、成果物と確認方法を定めた小さな手順を組み立てる。

## 3. 委譲する場合の責任を明確にする

委譲は、利用環境で許可され、独立した作業として効果がある場合に行う。すべての仕事に並列実行や複数モデルを要求しない。

- 異なる範囲を調べる分担と、同じ問題の代替案を比較する分担を区別する。設計に争点が残る場合は、根拠に対する独立した批判・レビューを行う。
- 目的、所有するファイル、変更禁止範囲、入力資料、適用原則のID、完了条件、確認方法を渡す。大量の本文を転送するより参照先を示す。
- 同じファイルへ複数の書き込み担当を置かない。ほかの担当者の変更を戻さないことを明示する。
- 利用できるモデルと既存の設定に従い、特定の製品やモデルを固定しない。
- 親が成果物と検証結果を確認し、自分の判断で報告する。担当者の「完了」をそのまま受け入れない。
- 中断・再開で指示が欠けた場合は、最新の範囲と条件をまとめ直して渡す。

## 4. 検証と判断の記録を残す

- 変更した利用経路に適した検証を実行し、期待した結果と比較する。必要なチェックが成功した後、理由なく広範な検証を繰り返さない。
- レビュー前に不要なコード、過剰な抽象化、重複、不要なコメントを整理する。コメントは、コードから読み取れない理由や外部制約を説明するものに絞る。
- コミットが依頼・許可されている場合は、その前に差分を整理する。手順にコミットが登場しても、現在の禁止指示を優先する。
- 長期・自律作業では、採用した判断、代替案、根拠、検証結果を後から確認できるようにする。会話全文や内部の思考過程は保存しない。
- 将来も使う決定・発見はOKFへ、一時的な進捗や再開手順はcheckpointへ残す。記録のために依頼範囲を広げない。
- 作業中にスキルの不具合を見つけたら、原因と影響を明示する。修正が依頼範囲内なら区別できる変更として直し、範囲外なら未対応事項を示す。独断で別のPRを作らない。

## 5. 結果を伝える

利用者と保守担当者に何が変わるかを先に説明し、変更理由、実行した検証、未確認事項を続ける。

- 短い平易な文で、一文に一つの内容を書く。簡潔にするために必要な条件や不確実性を落とさない。
- 事実には根拠を添え、推論や推測にはその区別を付ける。リンクや参照先を捏造しない。
- 判断を変えた原則は、名前と具体的な選択を示す。本文を読んでいない原則や、名前だけを並べた一覧を適用実績として報告しない。
- 自分で実行可能な確認を、理由なくユーザーへ渡さない。実行できなかった確認はその制約を示す。
- 提案を無条件に肯定しない。必要性がない変更や要件に合わない方針には、根拠を示して異なる判断を伝える。

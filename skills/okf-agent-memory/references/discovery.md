# 検索・参照

## 検索してから本文を読む

設計判断、既存の要件・規約に関する質問、新しいconceptの作成では、まず関連する語で `search` する。最初は `--limit 3` でタイトルと `description` を確認し、必要なconceptだけ `show` で取得する。候補が足りなければ語を変えるか件数を増やす。

`search` はBM25による関連度検索、`show` は本文・frontmatter・入出方向の関連リンクの取得に使う。本文と直接のリンクで判断できれば、関係する文書すべてを読み込む必要はない。同じ話題が見つかったら、作成ではなく更新を検討する。

## 変更するコードから調べる

対象領域を初めて変更する前に、`search --for-path` で `code_refs` に対応するconceptを取得する。これはキーワードを必要としない逆引きで、`hold`、`constraint`、`context` の順に確認する。話題検索の3件制限を、適用される制約の確認に流用しない。

| `governance` | 扱い |
| --- | --- |
| `hold` | 対象操作の保留。文書の適用範囲と解除条件を確認し、ユーザーの明示的な承認なしに対象操作を進めない。既に当該保留を踏まえた承認があれば繰り返し確認しない |
| `constraint` | 対象に適用される行動・禁止事項を守る |
| `context` | 判断の背景として参照する |

省略時は `context`。`rule` というtypeやディレクトリ名だけで強制力を推定しない。`code_refs` のない全体ルールはパス検索だけでは拾えないため、既知の適用文書や話題検索でも確認する。

文書が矛盾したら、対象範囲、明示された後継関係、ユーザーの指示を確認する。検索順位や更新日時だけで、どちらが有効か決めない。`draft`・`deprecated`・期限切れを現行の確定事項として扱わず、期限切れだけで制約や保留が解除されたとも判断しない。

## bundleの境界

対象bundleは明示し、別のプロジェクトの知識を混ぜない。配布文書が `.space/babel/vendor/<配布元>/` に配置されている場合、そのbundleもCLIで検索し、プロジェクト固有の文書と出所を区別する。

利用先の補足はプロジェクト側に記録する。配布文書そのものの更新を依頼されていなければ、配布元の本文を変更しない。

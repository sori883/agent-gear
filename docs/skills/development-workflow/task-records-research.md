# タスク進捗・作業資料・永続知識の分離に関する調査

2026-09-22。利用先へ配布する開発フローの記録方式を検討する調査メモ。ユーザーは、作業の記録を一時的なタスクとして残し、構成を選んだ理由などの確定した判断をOKFへ残す案について、反証も含めた調査を依頼した。本書の推奨は未採用であり、全体フロー・ひな形・設計正本の変更を意味しない。

同日追記：その後のユーザー指示により、OKFをシステムの設計・構成・歴史で整理する方針を[設計資料](../../development-workflow-design.md)へ反映した。以下は調査時点の比較として保持する。タスクの最小項目への軽量化やアーカイブ方法は引き続き提案段階。

同日再追記：task.mdは標準（中規模）・大規模で作成し、小規模では新規作成しない方針を採用した。小規模な子は台帳または親への報告で追う。以下の作成条件に関する提案より、現行の全体フローを優先する。

## 結論と確度

タスクの進捗、作業中の詳しい資料、後の仕事で使う知識は、目的と更新期間を分けることを推奨する。ただし、毎回三種類のファイルを作る必要はない。タスクは短い目的・完了条件と現在地を持ち、詳しい調査・設計・検証は必要な場合だけ別資料にする。OKFへは、将来の判断や作業に必要な確定内容を整理する。

「タスクの細かいゴールを永久保存しない」と「実行中のゴールを明確にしない」は別である。前者は妥当だが、後者は完了判定や引き継ぎを曖昧にする。実行中には短い目的と確認方法を保ち、終了後に知識へ残すかを別に判断する。

この結論は、後述の一次資料と現行文書の照合からの設計上の推奨である。本プロジェクトで記録方式を比較実験した結果ではなく、作業時間や誤完了率の改善は未測定。

## 現行の設計を評価する

[設計正本](../../architecture.md)は、作業中の記録、checkpoint、OKFを既に区別している。[全体フロー](../../../skills/development-workflow/references/workflow.md)も、短い内容はまとめ、空の文書を増やさず、後の仕事に必要な結果を整理する方針である。分離方針をゼロから追加する必要はない。

一方、[task-template.md](../../../skills/development-workflow/assets/task-template.md)には、依頼整理、範囲、受け入れ条件の表、工程選択の表、進捗、未決事項があり、末尾では後続の判断・結果・証拠の追記も案内している。[intake.md](../../../skills/development-workflow/references/intake.md)は省略を認めるものの、条件IDなどの細かさを短い依頼にも持ち込みやすい。これは本文の構成から予想される負担であり、実際に全項目を埋めてしまう頻度は未検証。

[OKFの保存判断](../../../skills/okf-agent-memory/references/remember.md)には、作業を終えたことだけを理由に文書を作らない、と既にある。全体フローの作業結果の保存先を、タスクごとに新しいconceptを作る義務と読ませないことが重要になる。意味のある判断や設計は残したい、という既存の希望は維持できる。

## 三つの案を比較する

| 案 | 良い点 | 問題・向く条件 |
| --- | --- | --- |
| 現行のtask.mdへ短い内容をまとめる | 入口が一つで、小さな仕事の参照漏れを減らせる | 詳細な設計や履歴が増えると現在地を探しにくい。短い仕事には引き続き有効 |
| pstackと同じ種類の記録を毎回そろえる | 情報の用途と更新先が明確になる | pstack自体も毎回すべてを要求しない。少量の情報を分散させ、リンクや同期の手間を増やす |
| 薄いタスクを入口にし、資料を必要時だけ分け、知識をOKFへ整理する | 現在地を短く保ち、設計・知識を独立して参照できる | 何を別資料・OKFへ残すかの基準が必要。入口のリンクと完了時の整理が抜ける可能性は残る |

三つ目を推奨する。短い仕事なら一つ目と同じ物理配置でもよい。「進捗と知識の責務を分けること」と「情報ごとにファイルを増やすこと」を混同しない。

## 推奨する記録の境界

以下は設計案であり、現在の保存先を移行したものではない。

| 記録 | 答える問い | 持つ内容 | 終了後の扱い |
| --- | --- | --- | --- |
| タスク | 今回何を終わらせるか。どこまでできたか | 一文の目的、完了を確認する方法、短い作業一覧と状態、必要な担当・阻害要因、成果物と結果への参照 | 終了状態と短い結果を残して通常の進捗表示から外す。知識検索へ自動登録しない |
| 作業資料 | 何を調べ、どう設計し、何を確かめたか | 必要な調査結果・比較・設計・検証証拠。既存Issue・PR・CI・仕様書があれば参照する | 成果物として必要なものと、結論の根拠を保持する。すべてを永続知識に変換しない |
| OKF | 後の仕事で何を知っておくべきか | 採用・見送りの判断と背景、現在の構成、再発防止に使う原因・結果、再利用する手順 | 話題ごとの正本として更新・関連付けを行う。作業ごとに新規文書を増やさない |

checkpointはこの分類へ新たな作業履歴を加えるものではなく、既存の記録と実状態を使って再開できるようにする保存時点の要約とする。実施方法は引き続き[checkpoint-safely](../../../skills/checkpoint-safely/SKILL.md)が所有する。

### タスクとして残す最小の単位

一つのコマンドやファイル閲覧ごとではなく、結果を確認できるまとまりを一項目にする。「何をやったか」は、完了した項目に結果を一行と証拠への参照を付ければ追える。タイトルは「テストする」より「指定の入力で修正後の挙動を確認する」のように、確認対象が分かるものにする。

短い目的と完了条件は作業中に必要だが、別々の長い章や詳細な目標履歴は不要。既存のIssueや計画の条件を参照できれば複製しない。複数の条件を独立して追跡する必要がある場合にだけ条件IDと表を使う。

仮の例として「タスク進捗と知識の保存範囲を設計する」なら、目的と終了条件を各一文にし、「現状確認」「案の比較」「選択した案の文書化」を状態付きで持つ。比較の本文はこのような調査資料へ置き、採用後に選択理由をOKFへ整理する。これは説明用の例であり、今回の設計が採用済みという記録ではない。

### 規模だけで保存方法を決めない

| 条件 | 推奨する記録 |
| --- | --- |
| 一回で終わる明白な変更・回答 | 会話内の短い作業記録や利用可能なTODOで足りる。専用ファイルは一律に作らない |
| 複数工程、回答待ち、翌日への継続、担当交代 | 既存のIssueまたは薄いタスクファイルなど、次の担当が読める記録を持つ |
| 複数の独立した納品単位・担当・依存関係 | 親子タスクと管理台帳。設計や検証本文は参照する。CLIはこの責務を支援する |
| 小さくても重要な設計判断や重大な変更 | 行数にかかわらず必要な理由と証拠を残す。タスクの事務項目を増やすこととは分ける |

CodexとClaude CodeのTODOについて、セッション間・親子間・製品間での可視性と保存保証は今回検証していない。これらをまたぐ作業の正本として、会話内TODOだけに依存する設計はまだ採らない。進捗の正本は一つにし、ファイルとUIの両方へ独立した状態を書かせない。

### 更新担当と保存期間

記録ごとに一人の更新担当を決める。全体のタスク記録が一つなら親が子の結果を確認して更新する。独立した子タスクの記録を持つ場合だけ、子が自分の記録を更新する。短い調査を委譲するたびに子のtask.mdを作ることは推奨しない。成果物の作成担当と、共有の進捗台帳へ反映する担当は同一でなくてもよい。

「一時的」は作業の終了で役割が終わるという意味であり、自動削除とはしない。終了後は作業中の一覧から外し、必要時だけ参照できるようにする。保持期間や削除方法は別途決める。未完了の引き継ぎ、未整理の重要な判断、OKFから参照している唯一の証拠がある記録を削除対象にしない。

作業の目的をすべてOKFへ転記する必要はない。ただし「なぜ依存をスキルごとに分けたのか」を説明する際の「配布先の依存へ混ぜず、単独で動かす」といった継続的な目的・制約は、判断の背景として残す。途中のタスクが読めなくても最終判断を理解できる内容にする。

## 反例と残る検証

| 疑ってみた案 | 反例と判断 |
| --- | --- |
| OKFだけあれば進捗は不要 | 現在の設計理由は分かっても、未検証の変更や残りの作業は分からない。継続する作業には進捗が必要 |
| 会話・Git履歴だけで全部追える | 作業中の未コミット変更や中止した案、未実施の条件を再構成する負担が残る。短い作業には使えても一律の代替にしない |
| タスクのゴールを省けば軽くなる | 修正・調査・設計のどこで終える依頼か分からなくなる。長い説明を省いて短い終了条件は保つ |
| 判断は確定してからだけ書けばよい | 長い検討の途中で、却下理由や観測条件が失われ得る。意味のある途中判断は作業資料へ残し、OKFへの登録時期と分ける |
| 最終結果なら全部OKFへ入れてよい | 誤字修正や反復的な確認まで一件ずつ知識化すると、後の作業に必要な内容を探しにくくなる恐れがある。既存の保存判断に従い選別する |
| タスクと資料を必ず分ければ明快になる | 一行の結果を別ファイルへ逃がすと参照の手間が勝る。独立した読者・更新・分量があるときに分割する |

これは机上の反例照合である。採用前後の試行では、誤字修正、翌日再開する不具合修正、設計調査、複数担当の変更を対象に、記録量、同じ状態の二重記入、再開時の再調査、未検証の完了扱い、判断理由の取りこぼしを比較するとよい。固定の改善率や最適なファイル数を今の根拠だけで決めない。

採用する場合の変更候補は、全体フローの「タスク記録を持つ条件」とOKFへの保存判断を明瞭にし、intakeとtask-templateを最小項目中心にすること。CLIの新設、保存形式の変更、既存記録の削除を先に行う必要はない。設計正本とObsidianの設計コピーへの反映は、調査結果から採用方針が決まった段階で行う。

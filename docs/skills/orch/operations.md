# orchの容量・履歴保持と手動アーカイブ

orch初版は履歴を削除せず、作業のまとまりごとに台帳を区切って使う。完了した台帳は全履歴と証拠を保持し、次の独立した仕事では別のstoreを明示して初期化する。進行中の依存を分断するために台帳を移すことや、state.jsonの一部を切り取ることはしない。

この文書は開発・運用判断の記録であり、配布するスキルには含めない。実際のコマンドと復旧条件は[CLI資料](../../../skills/orch/references/cli.md)、保存機構の確認範囲は[実装記録](implementation.md)を参照する。

## 2026-09-23の測定

[測定スクリプト](../../../scripts/bench-orch.ts)は一時ディレクトリにCLIをnode_modulesなしで複製し、コピー前後のソースのハッシュを照合する。同じ一時領域へ合成の成果物・証拠・台帳を作り、登録から更新まで実際のCLIを別プロセスとして呼ぶ。state.jsonを直接生成・編集して件数を増やしていない。実プロジェクトの台帳と測定用の台帳は別である。

```sh
bun scripts/bench-orch.ts --sizes 10,100,300 --samples 5 --out /tmp/orch-benchmark.json
```

測定は同じ台帳を段階的に増やし、子unitを10・100・300件とする。別に統合担当の親unitが1件ある。子の20%を提出・受け入れ済み、20%を中断、60%を実行中とし、完了した子の半分はreopenを経た2試行分の記録を残す。ローカルの成果物と検証証拠を持つ。親子以外の追加の依存、深い親子、外部参照、大容量の添付はこの測定に含めない。

status、unit ready、1回の工程進捗更新、exportを各5回測定する。Bunプロセスの起動・JSON読込・検証・保存または表示を含む経過時間であり、内部関数だけの時間ではない。OSのファイルキャッシュを消去せず、測定直前にもCLIで登録している。exportは直前の更新で進んだ新しいrevisionに出力し、既存出力への同一性確認だけで済ませない。p95は5回中の最大値になるため、長期間の分位点を推定するものではない。

測定結果の数値と実行環境は[機械可読の結果](benchmarks/2026-09-23-m4.json)に保持する。実行時のCLI全ソースのSHA-256も含め、測定の途中でコピーしたソースが変わっていないことを確認する。環境はApple M4、メモリ16 GiB、macOS/Darwin 25.5.0 arm64、Bun 1.4.2。ほかの開発作業も動いているホストであり、専有環境の性能保証値ではない。

| 子unit数（別に親1件） | 全試行数 | 保存操作数 | state.json | status | ready | 工程更新1回 | export |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 12 | 46 | 0.14 MiB | 46.4 ms | 47.3 ms | 46.9 ms | 50.2 ms |
| 100 | 111 | 393 | 1.22 MiB | 47.0 ms | 46.5 ms | 48.1 ms | 48.6 ms |
| 300 | 331 | 1,158 | 3.62 MiB | 61.1 ms | 61.4 ms | 64.1 ms | 59.3 ms |

時間は各5回の中央値。300子unit時の最大値は順に68.7・62.4・68.0・66.3 msだった。15回分のexportを含むstore全体は約4.05 MiB。初期化・登録・測定・並行確認を含めた全実行は約76.9秒で、1,226回のCLI起動を行った。台帳全体の読み書きによる利用困難な遅延は、この条件では観測していない。

同時更新は6個の独立プロセスが同一台帳へ別々の報告を送る試験である。LOCKEDには同じ操作ID・同じ入力で上限8回の再試行を行った。計15回のLOCKEDによる再試行を経て約856 msで全件保存され、revisionは1,158から1,164へ増えた。全操作と報告が1回ずつ存在し、成功操作の再送はreplayedとなり、state.jsonのハッシュが変わらないことを確認した。最後のdoctorの問題・ロックはともになし。ロック競合時のCLI内の自動再試行や、長期間の高頻度書き込みを確認したわけではない。

スクリプトの型検査にはリポジトリの`bun run typecheck`を使用した。[検証記録](benchmarks/2026-09-23-verification.txt)に実行内容と主測定結果のハッシュを残した。測定は一時領域だけで実行し、成功時に測定用の成果物・台帳を削除する。調査のため残す場合は`--keep-temp`を付ける。失敗時は一時領域を残してパスを表示する。台帳の削除機能を製品CLIへ追加したものではない。

## 容量の判断と見直し時点

台帳の件数だけを上限にしない。操作履歴には再送応答用の当時の結果も保存するため、同じunitを繰り返し変更すると、unit件数が一定でも容量は増える。試行数、操作数、成果物を照合する回数、依存の構造も所要時間に影響する。

本測定の最大件数までを短時間の動作確認範囲とする。受け入れ可能な待ち時間は利用環境で決め、例えば通常の単発コマンドが継続して1秒を超える、state.jsonが10 MiBを超える、LOCKEDの再試行が頻発するときに再測定する。1秒・10 MiBは運用上の見直し目安であり、実装の制限値でも、そこまで常に高速という保証でもない。

最初の対策は、不要な定期ポーリングや細かな同内容の更新を減らし、依存が閉じる仕事の区切りを明確にすること。exportは報告・引き渡し等で必要な時点に出し、全操作のたびに複製を増やす必要はない。進行中の台帳が遅いという理由だけで履歴を削除しない。問題が再現したら、状態検証・探索・証拠のハッシュ計算・JSON保存のどこに時間を使うかを分けて計測する。その根拠なしに保存形式や一貫性の規則を変更しない。

## 保持するもの

| 対象 | 保持方法 |
| --- | --- |
| state.json | 完了後も全履歴を保持。古い試行・差し戻し・失効提出・通知・操作IDと応答も含む |
| exports/ | 人間が当時の一覧を読むための出力。state.jsonの代替や復元入力にはしない |
| task.md・設計・計画・証拠・提出物 | 当時の対象版を説明できる状態で保持。台帳の参照だけではファイル本体を保存したことにならない |
| 保存時点の目録 | project基準パス、元のstore、保存日時、revision、stateのハッシュ、実行環境・CLI版、参照ファイルと保存位置を記録 |
| OKF | システムの採用設計・理由・構成・重要な歴史を必要に応じて保存。作業台帳を丸ごと知識に複製しない |

初版には自動の保存期限、履歴削除、compact、別storeへのunit移植、TSVの逆インポートを追加しない。削除時期を将来決める場合も、証拠・再開・監査に必要な期間を確認した別の変更として扱う。

## 完了したstoreを別置して切り替える

1. **仕事の区切りを確認する。** 必須の子を親が受け入れ、親自身の完了判定も終える。未解決のgate、未処理の報告、今後再提出を待つ仕事が残る間はアーカイブへ進まない。中止した仕事がある場合は、親が除外理由と条件をどこで扱ったかを残す。
2. **書き手を止める。** 全担当へ終了を共有し、旧storeへ書くプロセスがないことを確かめる。doctorでロックと参照を確認する。稼働中のロックを消したり、コピー中に書き込みを続けたりしない。
3. **終了時点を保存する。** status・ledger summary・inbox list・gate listを確認し、最後のexportを作る。state.json、exports、参照する成果物・証拠と目録を別のアーカイブ先へコピーする。元のstoreとコピーのstateハッシュが一致し、必要な証拠が存在することを確認する。コピーを作ったことを理由に元データを削除しない。
4. **アーカイブを読み取り専用にする。** コピー側のファイル・ディレクトリへの書き込み権限を外し、アクティブなstoreとは異なるパスに置く。これは誤更新防止であり、権限を持つ所有者が戻せない仕組みではない。アーカイブにinit、assign、reopen、export等の書き込みを実行しない。
5. **次のstoreを明示する。** 次の独立した仕事に別の空パスを選び、init --projectで初期化する。各担当へ正確な--storeまたはORCH_STOREを渡し、旧環境変数を引き継いだままにしない。親のtask.mdにも新しいパスを記録する。
6. **継承する成果を新しい契約にする。** 旧成果が入力になる場合は、どの版の成果を使うかを新unitのcontractFilesや検証条件に明示する。別storeのunit IDをdependency addに渡して依存がつながったと扱わない。継承先でも開始と確認を行い、旧版の合格記録を無条件に移植しない。

保存先の例は `.space/tasks/archive/<closed-work-id>/orch/`、新しい台帳は `.space/tasks/<next-work-id>/orch/`。これは保存先の例であり、CLIが自動作成・移動する命名規約ではない。

### 参照パスの注意

state.jsonのprojectはinit時の絶対パスであり、相対参照はそこから解決する。storeのコピー先を変えてもprojectや絶対参照は書き換わらない。したがって、アーカイブしたstoreへのstatusが現在もacceptedを示すかは、元の参照先が当時のまま残っているかに依存する。後から元のコードを変更すればunknownや無効と見えることがあり、履歴が消えたという意味ではない。

移設先でCLIが自動的に参照を付け替える機能はない。保存用には当時の証拠もコピーし、元の参照と保存コピーの対応を目録へ残す。履歴の再確認では保存コピーのハッシュを台帳のdigestと照合する。パスが合わないことを解消するためにstate.jsonのprojectやdigestを直接書き換えない。元環境なしでの移設後の再検証が必要なら、参照の移行を扱う機能を別途設計する。

## 確認の限界

この結果は単一のmacOSホストとローカルファイルシステムでの短時間の試験である。日月単位の運用、他OS、低速ディスク、ネットワーク共有、電源断、深い依存や高密度の依存グラフ、数百試行を持つ1unitは未確認。自動アーカイブや復元機能を実装済みとは扱わない。

# orch CLIの設計

2026-09-23作成。レビューの4点を採用した設計。実装状況は[orchの実装記録](../orch/implementation.md)を参照する。[利用方法・責務・配置・実装範囲](orchestrator-design.md)と一緒に読む。本プロジェクト向けのコマンド体系であり、具体的な入力は[配布用CLI仕様](../../../skills/orch/references/cli.md)に定める。

## 1. 呼び出しと共通規則

実体は配布された`skills/orch/scripts/task.ts`をBunで起動する。以下の`orch`はその略記。

```text
orch --store <台帳ディレクトリ> [--json] <コマンド>
orch --store <台帳ディレクトリ> --actor <担当ID> --operation-id <操作ID> <更新コマンド>
```

- `--store`または`ORCH_STORE`で保存先を明示する。既定配置は`.space/tasks/.orch/`だが、通常の操作で勝手に初期化しない。
- `--actor`は記録上の操作主体。変更権限のある役割と照合する。確認の実施者と代理の記録者は別々に残せる。
- 更新コマンドは操作IDを持つ。同じID・同じ入力の再送は同じ操作の保存結果を返し、二重登録しない。この照合はversion検査より先に行う。同じIDを異なる入力へ流用した場合は拒否する。
- 担当・進捗・契約・受け入れを変更する操作は、対象の`version`または提出IDを指定する。古い値なら保存せず、読み直しを求める。書き込みロックだけで古い判断の上書きを正当化しない。
- 子の操作はunit IDと現在の`attempt`を持つ。担当IDは引き継げる役割名とし、操作するセッションも照合する。以前の担当・セッション・試行から遅れて届いた更新は拒否する。
- `--json`は構造化した全結果を返す。一覧の省略やページ分割を行う場合は件数と続きの取り方を返し、表示した分だけで全件とは扱わない。
- `get`・`list`・`counts`・`ready`・`check`・`summary`・`status`・`doctor`は読み取り専用。読み取りで出力ファイルや通知の状態を変えない。

具体的なJSON入力は`--input <file>`または標準入力から渡せる形を推奨する。複数の条件・工程・所有範囲を長いシェル引数へ展開しない。入力用JSONは操作のためのデータであり、unitごとに保管する成果物として必須にしない。

## 2. unitの操作

| コマンド | 主体 | 保存・表示する内容 |
| --- | --- | --- |
| `init --project <dir>` | 統括担当 | schemaVersion、対象プロジェクト、統括担当を持つ空の台帳を作る。既存の互換台帳なら内容を保つ |
| `unit add <id>` | 親・統括担当 | 目的、規模、親、作業担当・記録担当、所有範囲、条件、文書参照を登録。初期状態はpending |
| `unit get <id>` | 読み手 | 指定unitの契約、現在の試行、工程、進捗、条件別判定、受け入れ、前提不足を表示 |
| `unit list` | 読み手 | 親の配下、状態、担当、作業グループで絞り込んで表示 |
| `unit counts` | 読み手 | 作業状態別の件数と、現在有効な受け入れ件数を別々に表示 |
| `unit update <id>` | 親・統括担当 | 目的・条件・所有範囲・参照等を理由付きで変更。契約の版を更新 |
| `unit assign <id>` | 親・統括担当 | 担当・記録担当を割り当てる。交代時は旧担当の書き込み終了確認を参照し、試行を切り替える |
| `unit start <id>` | 記録担当 | 前提を再照合し、使う依存先の提出・成果物の版を記録してrunningへ進める |
| `unit set <id>` | 記録担当 | 待ち・中断・中止、理由と次の操作を記録。completedの直接指定には使わない |
| `unit stage <id> <工程>` | 記録担当 | 工程の実施・統合・再利用・省略、その理由、実行状態、成果物参照を更新 |
| `unit submit <id>` | 記録担当 | 現在の成果物・版・報告・確認記録を固定した提出を作り、completedと報告通知を一緒に保存 |
| `unit accept <id> --submission <id>` | 親・統括担当 | 指定した提出と証拠を確認した理由を残し、受け入れる。対応する完了通知を処理済みにする |
| `unit return <id> --submission <id>` | 親・統括担当 | 不足と再開条件を記録して差し戻す。子の進行状態は書き換えず、完了通知を処理済みにする |
| `unit reopen <id>` | 記録担当 | 差し戻し・変更・前提の再確認に伴い新しい試行を作り、pendingへ戻す。理由を必須にする |

初版はunit ID・親子関係を登録後に付け替えない。分割し直す場合は元のunitを理由付きで中止し、新しいunitと関連付ける。旧記録・成果物は消さない。計画変更や再割当では、単なる説明文の修正と、条件・入力・担当の変更を区別する。後者は実行中に強行せず、停止確認後に試行を切り替える。

親を持たないunitも統括担当の役割を持ち、単独作業なら作業担当と兼ねる。統括担当の再開・引き継ぎは旧セッションの停止確認と引き継ぎ根拠を記録して行う。人間への再承認を一律に追加せず、既存の依頼・引き継ぎの権限内で操作する。セッションの引き継ぎもassignの対象とし、初期化し直して旧記録を捨てない。新セッションによる最初のassignだけは、同じ統括役割、旧セッションの一致、現在のversion、旧処理の停止と引き継ぎ権限の根拠がそろった場合に許可する。交代を一度の更新で確定し、旧セッションの通常更新を拒否する。通常の更新にはこの例外を適用しない。

### 作業状態の遷移

| 操作前 | 操作 | 操作後・条件 |
| --- | --- | --- |
| pending（未開始） | start | 前提を初めて固定してrunningへ進む |
| waiting・paused | start | running。契約・入力版が開始時と一致する場合だけ同じ試行で再開。不一致ならreopenを要求 |
| running | set | waiting・paused・cancelled。理由を記録 |
| pending・waiting・paused | set | waiting・paused・cancelled。変更理由を記録 |
| running | submit | completed。現在の版に対する終了条件、必要な工程、依存・子の受け入れが満たされていること |
| completed | accept・return | 作業状態はcompletedのまま、提出の受け入れ状態だけを変更 |
| completed・paused・waiting・cancelled | reopen | 新しいattemptのpending。中止後の再開は親の範囲確認を参照 |

前提が変わった実行中のunitは、担当が中断してからreopenで新試行を作る。startは既存試行の入力版を更新しない。CLIは動いているエージェントを停止できないため、派生表示で前提の不一致を示し、その状態での提出・受け入れを拒否する。旧試行の証拠は保持し、再利用できるものだけを担当が照合して新試行へ参照付きで記録する。

工程は既存の8工程に限定する。省略した工程は実行状態を対象外として表示し、実行済み件数には入れない。再利用の場合は適合性確認の状態を持つ。工程の完了から、unitの完了や対象の合格を自動推論しない。

## 3. 依存・確認・報告・判断待ち

| コマンド | 主体 | 機能 |
| --- | --- | --- |
| `dependency add <unit> --on <先行unit>` | 親・統括担当 | 必要な成果物・受け入れ・条件別判定を依存として登録。親子関係を含め循環を検査 |
| `dependency remove <unit> --on <先行unit>` | 親・統括担当 | 理由付きで依存を解除。実行開始後なら入力変更として再確認を要求 |
| `unit ready` | 読み手 | pending・waitingから記録上の着手候補を表示。外れたunitの不足も表示可能にする |
| `ledger record <unit>` | 許可された確認担当・記録担当 | 試行、対象・版、条件ID、判定、確認方法・環境・時点、証拠または未確認理由を記録 |
| `ledger check <unit>` | 読み手 | 指定した試行・対象版の条件別判定と不足を返す。テストは実行しない |
| `ledger summary` | 読み手 | 条件別判定を集計。現在の提出と過去の試行を区別 |
| `inbox push <unit>` | 作業担当・記録担当 | 途中報告、支援依頼等を通知として登録。完了報告はsubmitを使う |
| `inbox list` | 受信担当 | 自分宛ての未処理通知を読む。読み取りで削除しない |
| `inbox ack <message-id>` | 受信担当 | 対応した理由・参照を記録し、処理済みにする。履歴は保持 |
| `gate park <id>` | 作業担当・親 | 問い、選択肢、推奨案、影響するunit、回答者を登録 |
| `gate list` | 読み手 | 未解決の問いと、回答待ちになっているunitを表示 |
| `gate resolve <id>` | 親・統括担当 | 得られた回答とその根拠を記録。依存する仕事は担当が前提を照合して再開 |
| `status` | 読み手 | 親子の進捗、提出と受け入れ、条件別判定、判断待ち、未処理報告を表示 |
| `export` | 統括担当 | 一つのrevisionからunits.tsv・ledger.tsv・status.mdを生成 |
| `doctor` | 読み手 | schema、参照、状態の整合性、ロック情報、ローカル成果物の参照切れを確認 |

依存の追加・解除、gateの変更も対象unitの契約・前提を変える。現在の実行へ無条件で差し込まず、状態と版を照合する。readyで候補になった後もstartが保存時点の前提を再確認する。waitingの理由が手動確認なら、再開条件の確認記録がない間は候補に含めない。pausedは明示的に再開するまで候補に含めない。

ledgerの対象はコード・文書・環境等。PR番号を必須にしない。コードの版はGitのSHA、文書は内容のハッシュ等で特定する。未コミットのコードではHEADのSHAだけを変更後の版として使わず、対象ファイルや差分を識別するハッシュも添える。実装前に入力型としてコード・文書・外部対象の版の表現を固定する。

pass・failには実際の証拠参照を必須とする。unknownは未確認の理由、not-applicableは適用しない理由を持つ。ファイルの存在確認は行えるが、内容の妥当性や外部URLの真正性をCLIが証明したことにはしない。

確認記録は上書きせずIDを持って追加する。同じ条件を再確認するときは置き換える記録IDを明示し、同じ対象・試行・条件であることを検査する。新しい提出は各条件で現在有効な確認記録のみを使用できる。置き換え済みの記録は拒否し、同じ有効記録から競合する二つの置き換えも許さない。提出は使用した記録IDを固定し、後から追加された別の判定で過去の提出を書き換えない。completed・cancelledの試行に現在の結果を追加する場合は、先にreopenして新試行へ記録する。

acceptは「報告を受け取った」だけでなく、登録された依頼の終了条件との照合を表す。受け入れは提出ID・契約の版・入力の版に結び付ける。条件が変わった場合や古い試行では、以前のacceptedを現在有効な受け入れとして集計しない。

inboxの完了通知は、accept・returnで判断を保存したときに処理済みにする。reopenや試行の切り替えでは旧提出を現在無効とし、未処理の旧完了通知をobsoleteへ移す。この更新は新試行の作成と同時に保存する。再提出前は後続の提出IDを捏造せず、新しい提出ができた時点で関連付ける。以前の受け入れ判断はそのまま履歴に残す。ackだけで完了通知を隠すことは拒否する。途中報告のackは作業状態や受け入れを変更しない。重複して通知を読んでも、操作IDと提出IDによって二重の受け入れを防ぐ。

gateの回答は人間の回答や確認できた事実への参照を持つ。既定案の自動採用、時間経過による承認、回答後の自動起動は行わない。同じ問いを開き直す場合も以前の回答を保持して版を更新する。

## 4. 管理データの構成

state.jsonはschemaVersionと台帳全体のrevisionを持ち、次の情報を保存する。unitの最新表示と、過去の試行・提出を区別する。本文は参照先に置く。

| 記録 | 必須となる情報のまとまり |
| --- | --- |
| 台帳 | schemaVersion、revision、対象プロジェクト、統括担当、作成・更新時点 |
| unitの契約 | ID、親、規模、目的、統括・作業・記録・確認担当、所有範囲、文書参照、条件、契約の版 |
| 条件 | 条件ID、説明または説明への参照、依頼の終了条件か対象評価か、終了に必要か、必要な判定 |
| 試行・進捗 | attempt、担当セッション、記録のversion、作業状態、工程の選択と実行状態、開始時の入力版、理由・次の操作 |
| 依存 | 後続・先行unit、必要な成果物と条件、登録理由、版 |
| 確認記録 | ID、unit・attempt・条件・対象版、判定、方法・環境・時点、証拠、実施者・記録者、置き換え先 |
| 提出 | ID、unit・attempt・契約版、入力・出力の版、使用した確認記録ID、報告本文または参照、提出者・時点 |
| 受け入れ | 提出ID、pending・accepted・changes-requested、判断者・理由・時点 |
| 通知 | ID、送受信担当、unit・attempt、種類、本文または参照、処理状態、処理結果への参照 |
| gate | ID、問い・選択肢・推奨案、影響するunit、回答者、状態、回答・根拠・時点・版 |
| 更新の記録 | 操作ID、入力の識別値、操作主体、対象、変更理由、更新前後のrevision、保存結果への参照 |

条件を説明する文書だけを変更して契約の版を据え置かない。参照する条件部分の版を契約に結び付け、開始・提出・受け入れで照合する。対象成果物が変わったときも、更新した版を明示する。ローカルファイルは読み取り時に照合できるが、CLIがあらゆる外部成果物の変更を自動検知するとはしない。

終了に必要な条件は原則passを求める。対象外を認める条件は契約に明示し、not-applicableには理由を要求する。レビュー対象のfail・unknownを報告する依頼では、その評価条件を必須passにせず、報告内容を終了条件にする。各unitは少なくとも一つの終了条件を持つ。

親の子unitは既定で全て完了・受け入れを必要とする。中止した子を全体の完了条件から外す場合は、親の契約変更として理由と元の条件の扱いを記録する。必須の子を中止しただけでは全体を完了にできない。

ファイル参照は対象プロジェクトを基準に解決し、参照ごとに基準を明示する。worktree内だけに存在する成果物は作業場所を併記し、親が読める形で保存・引き渡す。外部URLも参照として保持できる。CLIが書く範囲は指定された台帳とexportに限定する。

## 5. 保存・競合・復旧

一回の更新では、台帳のロック取得、現在状態の読み取り、担当・試行・versionと不変条件の検査、変更後全体の検証、一時ファイルへの保存、正本への置き換えを順に行う。提出・通知・操作IDの記録は同じstate.jsonに含め、片方だけ保存される状態を作らない。

ロックは台帳の場所に対して一つとし、取得できなければ競合として終了する。生きているロックを奪うforce操作は初版に設けない。異常終了後の残存ロックはdoctorで所有プロセス等を確認し、すべての書き手が停止したことを確認して復旧する手順をスキルに定める。根拠がない自動削除はしない。

一時ファイルは正本と同じファイルシステムへ置き、保存を確認してから置き換える。失敗時は成功を返さず、途中ファイルから正本を推測・再構成しない。プロセス停止で壊れたJSONを正本にしないことを初版の必須条件とする。電源断まで含む永続性の保証はファイル・ディレクトリの同期とOS別試験で範囲を確定し、実施前に保証済みとしない。

exportは読み取った一つのrevisionを固定し、一時ディレクトリで全出力を完成させてから`exports/<revision>/`へ配置する。途中失敗では完成した出力として公開しない。TSVはUTF-8、ヘッダー付きとし、セル中のタブ・改行・バックスラッシュのエスケープを固定する。逆インポートは初版に含めない。

未知のschemaVersionや壊れた正本を見つけた場合は、診断を返して更新を拒否する。既存データの暗黙の初期化、修復、破棄は行わない。初版に自動アーカイブ・削除を設けず、履歴の保持期間は実運用後に決める。

## 6. 出力と終了コード

| 終了コード | 意味 |
| --- | --- |
| 0 | 操作・問い合わせが成功。返された成果判定が合格という意味ではない |
| 1 | 保存や入出力等の実行エラー |
| 2 | 入力不正、対象なし、不変条件違反 |
| 3 | ロック、古いversion・attempt等の競合。再取得・確認が必要 |

JSON出力は成功時に台帳revisionとdata、失敗時に安定したエラーコード・理由・該当unitを持つ。ledger checkは対象unitがあっても証拠がなければunknownを返す。未確認・不合格と、CLIの実行エラーを区別する。集計には対象の版・範囲を含める。

## 7. 実装前に固定する詳細と検証

この文書は振る舞いと保存境界の設計。初版の入力JSON、versionを要求する操作、参照する版、エラーコード、TSV列はschemaVersion 1として実装した。利用時の例は配布用cli.md、開発時の確認結果と制約は実装記録へ分けている。

優先してテストするのは、無効な遷移、子による親の更新、古い試行からの遅延報告、依存の循環、版が変わった証拠、受け入れ前の後続開始、二重提出、保存中断、未処理通知の保持である。最終的に、PRのない設計・レビュー作業と複数子unitの統合を実コマンドで通す。

ここに記した検証は予定であり、CLIや並列エージェントを動かして確認した結果ではない。

各工程の詳細ファイル、ひな形、task CLI、setup、配布生成、カタログ、インストール、コミット、PRは今回の対象に含めない。how・why・system-blueprint・checkpoint-safely・OKFの実装も変更しない。

## 責務分離の判断

全体フローを追加するだけではuse-principlesの進行指示が残るため、両者の分離と導入用テンプレートの接続を同じ変更に含めた。原則・ルールの全件候補検索、本文による適用条件の確認、変更対象パスによる制約の確認を保ち、コマンド書式はOKFスキルへ集約した。配布用本文にあった文書作成側の方針も取り除き、利用者に必要な読み取り手順だけを残した。

タスク成果物の新規保存先は `.space/tasks/<task-id>/task.md`、詳細は必要な場合だけ分割する。これはCLI台帳の保存形式を確定するものではない。CLIを利用できない場合は親の計画に依存・状態・担当・証拠を残して順次進める。CLIを必須にする目標と、現在利用可能な手段を区別する。

checkpointは既存スキルの保存手順に任せ、作業ログの正本にはしない。OKFには確定した結果と判断を整理して渡す。保存が許可されない依頼、保存の失敗、作業の未完了を成功に置き換えない。

## 進捗更新の責任とタイミング

2026-09-22。ユーザーの指示により、全体フローの共通ルールとして進捗更新を明文化した。子エージェント自身が自分のタスクを更新し、親は報告と証拠を確認して受け入れ確認・集約・全体の完了判定を更新する。委譲時にタスクID、更新先と担当範囲、報告先、共通ルールへの参照を渡す。

更新の節目は着手、工程・検証単位の終了、前提待ち・失敗、再開・差し戻し・範囲変更、中断・担当交代・終了とした。task-template.mdに更新担当・日時・台帳と報告先の欄を追加し、CLIを使う場合は台帳を状態の正本として参照する。

CLIを使わない場合、子のtask.mdが自分の進捗を持ち、親の計画は参照と確認時点の集約を持つ。CLIを使う場合も担当ごとの責任は維持するが、更新・排他の具体的な方式は今後のCLI設計対象である。子に書き込み権限がない場合や保存に失敗した場合は、更新できなかった内容を親へ渡す。通常の進捗更新でcheckpointを増やす指示は追加しない。

本文の机上確認では、次のケースを照合した。

| ケース | 記録と確認の担当 |
| --- | --- |
| 単独のタスク | 担当自身が節目で進捗と証拠を更新する |
| CLIなしで親子に分担 | 子が自分のtask.md、親が自分の集約と受け入れ確認を更新する |
| 子が作業完了を報告 | 親が証拠を確認するまで、受け入れ済みの完了件数に加えない |
| 親から差し戻し | 親が指摘を記録して返し、子が工程状態と次の操作を更新する |
| 子が記録を書けない・保存失敗 | 子が未更新の内容と理由を報告し、親が保存できた範囲を確認する |
| 担当交代 | 旧担当の書き込み終了を確認し、担当と更新先を引き継ぐ |

実エージェントによる並行更新やCLIの排他動作を検証したものではない。今回の変更は配布用の指示と設計資料であり、タスク管理CLIは実装していない。

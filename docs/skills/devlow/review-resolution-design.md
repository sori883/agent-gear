# 開発ワークフローの修正設計：依頼の完了・対象の判定・知識の保存を分ける

2026-09-23作成・反映。レビューで見つかった4点に対する設計。会話を読んでいない人が、変更後の使い方と修正範囲を理解するための資料である。全体フロー・各工程・タスクと計画のひな形へ反映済み。確認範囲は[実装・確認記録](implementation.md)に記す。

例えば、レビューでバグを見つけて報告した場合、「レビューの依頼は完了」「確認した対象は要修正」が同時に成立する。この区別を工程の進み方と記録欄へ反映し、確定した設計や知識を保存する責任も明確にする。

## 1. このワークフローで行うこと

devlowは、開発を依頼されたAIが、必要な作業を選び、結果を確認して利用者へ渡すための手順である。「機能を追加する」だけでなく、「設計だけ」「検証だけ」「レビューだけ」という依頼にも使う。

**タスク**は、目的と終了条件を持つ一件の仕事。**工程**は、その仕事の中で行う調査や設計などの作業の種類である。一つのタスクが必要な工程を通る。工程ごとに別のAIやファイルを用意する必要はない。

| 工程 | 何をするか | 次へ渡すもの |
| --- | --- | --- |
| 依頼整理 `intake` | 何をどこまで依頼されたかを整理する | 目的、範囲、終了条件、選んだ工程 |
| 調査 `investigate` | 現状と分からないことを調べる | 事実、根拠、残る不明点 |
| 設計 `design` | どのような構成にするかを決める | 候補の比較、採用した構成と理由 |
| 計画 `plan` | 作業を実行できる単位に分ける | 担当、順序、依存関係、検証の予定 |
| 実装・編集 `implement` | コード・設定・文書を変更する | 変更した成果物と差分 |
| 検証 `verify` | 実行や照合により、条件を満たすか確かめる | 方法、実際の結果、証拠、条件ごとの判定 |
| レビュー `review` | 成果物と根拠を読み、問題や見落としを評価する | 指摘、その理由、未確認の範囲 |
| 引き渡し `deliver` | 結果を報告・納品し、必要な知識を保存する | 完了した範囲、残件、成果物・知識への参照 |

**OKF**は、システムの構成・設計理由・重要な歴史を、後の作業でも参照できる文書として管理する仕組みである。作業途中の記録はタスク側、長く残すシステムの知識はOKF側に置く。

## 2. 今回解消する問題

修正前の本文にも、レビューだけの依頼に修正を追加しないことや、未実行の検証を確認済みと書かないことは定義されていた。今回、フロー図・記入欄・各工程の説明に残っていた次の曖昧さを解消した。

| 修正前の分かりにくさ | 修正で明確にしたこと |
| --- | --- |
| レビューだけの依頼も図では検証へ入り、修正へ戻る矢印がある | 依頼の種類から経路を選び、レビュー結果を報告して終了できる |
| タスク記録に「実行状態・確認結果」という一つの欄がある | 作業が終わったかと、対象が条件を満たしたかを別々に記録する |
| 設計工程の「OKFへ整理する」が、その場での保存にも読める | 各工程が候補を渡し、引き渡し工程が保存を担当する |
| 計画の成果物が「検証の証拠」と書かれている | 計画では必要な証拠を定め、実行後に取得した証拠を記録する |

8工程、規模による工程選択、タスクとOKFの保存先は維持する。新しい工程やタスク管理CLIは追加しない。

## 3. 依頼の種類で進む経路を決める

依頼整理で「今回渡すもの」と「終了地点」を決めてから、必要な工程へ進む。対象を理解するための短い調査は、各工程にまとめてもよい。

| 依頼 | 主な経路 | 問題が見つかったとき |
| --- | --- | --- |
| レビューだけ | `intake → review → deliver` | 指摘と限界を報告する。発見を理由に修正へ進まない |
| 検証だけ | `intake → verify → deliver` | 不合格や確認不能を報告する。発見を理由に修正へ進まない |
| 変更を完成させる | `intake → 必要なinvestigate・design・plan → implement → verify → 必要なreview → deliver` | 依頼範囲内で原因に関わる工程へ戻り、変更後に必要な確認を行う |
| 調査・説明だけ | `intake → investigate → 回答の根拠確認 → deliver` | 分かったことと不明点を回答する |
| 設計・計画だけ | `intake → 必要なinvestigate・design・plan → 成果物の確認 → deliver` | 依頼された設計・計画を見直す。実装の問題まで修正したことにはしない |

回答や設計の確認は、`verify`の役割として元の工程へ統合できる。レビューだけの経路でも、指摘の根拠は確認するが、レビュー開始前の別工程として検証を必須にしない。

フロー図では、報告を目的とするレビュー・検証の経路と、変更を完成させる経路を別の枝にする。確認対象の修正へ戻る矢印は、その変更まで依頼された枝に置く。設計・計画の成果物を見直す場合も、依頼された文書の範囲で戻る。検証が合格し、レビューが不要なら、直接引き渡しへ進める。図と本文の両方に同じ条件を書く。

例として「この変更をレビューして」と依頼された場合、バグを見つけたら、再現条件・影響・該当箇所を渡す。利用者から修正も依頼された時点で範囲と終了条件を更新する。もともと修正まで依頼されている場合は、既存の依頼範囲で続ける。

## 4. 作業の進行と対象の判定を分ける

### 記録する二つの状態

**進行状態**は「依頼された仕事がどこまで進んだか」。**成果判定**は「確認した対象が、どの条件を満たしたか」である。

| 記録 | 値 | 意味 |
| --- | --- | --- |
| 進行状態 | 未着手／実行中／判断・前提待ち／中断／完了／中止 | 依頼または工程の進み具合。完了は依頼された終了条件を満たしたこと、中止は取りやめが決まったこと |
| 成果判定 | 合格／不合格／未確認／対象外 | 条件を満たす証拠がある／満たさない結果を確認した／判定に足りる証拠がない／その条件が適用されない |

「対象外」は既存の検証資料の用語を使う。「未確認」は対象に問題があるとの判定ではない。適用される条件の確認を省略した場合は、対象外に変えず未確認とする。

レビューでは、既存の「引き渡し可能・要修正・確認待ち」も具体的な評価として残す。指摘がないだけで対象全体を合格にせず、評価した条件と範囲を明示する。評価基準が決まっていない説明には、無理に合否を付けない。

### task.mdの記入欄

冒頭の「状態」を「進行状態」に変更し、別に「成果判定」を設ける。成果判定欄には、対象・条件ごとの結果への参照と要点を記す。複数の対象や条件があるときは、「不合格1件、未確認2件」のように残し、一つの合否で覆わない。

受け入れ条件には、**依頼を完了とするための条件**を書く。検証・レビュー対象を評価する条件とは区別する。例えば「評価結果と限界を報告する」が依頼の条件、「一覧が指定の順序で表示される」が確認対象の条件となる。

工程選択表は次の5列にする。選択は工程を行うかどうか、実行状態はその作業の進み具合、確認結果は行った評価を表す。

| 工程 | 選択 | 理由・統合先・再利用する資料 | 実行状態 | 確認結果・参照 |
| --- | --- | --- | --- | --- |
| verify | 実施 | 一覧の並び順を確認する依頼 | 完了 | 並び順は不合格。条件ごとの結果を参照 |
| implement | 省略 | 今回は検証結果の報告まで | 対象外 | 対象外。修正済みとは数えない |
| deliver | 実施 | 結果と限界を報告する | 完了 | 報告済み。対象の不合格は残る |

省略した工程の「対象外」は、実行状態欄に記す例外的な表示とする。工程の完了件数に含めない。再利用では、既存成果物の適合性を確認する作業の状態と、その確認結果を別々に書く。

詳細な判定は、task.mdの「条件ごとの結果」または既存のverification.md・review.mdに一度だけ記録する。対象と版、条件の内容・識別子、判定、証拠、限界を対応付け、冒頭と工程表から参照する。新しい結果専用ファイルは必須にしない。

### 完了と不合格が同時に成立する例

利用者が「一覧の表示順を検証して結果を報告して。実行できない条件があれば理由も示して」と依頼した場合、次の記録で終了できる。これは記入例であり、実際の検証結果ではない。

```text
依頼の終了条件：指定した条件の確認結果と、確認不能の理由を報告する
進行状態：完了
成果判定：一覧画面・対象版r1について、不合格1件、未確認1件

条件ごとの結果：
  日付順で表示される → 不合格。対象版r1で順序の逆転を確認
  大量データでも表示できる → 未確認。必要なデータを利用できない

引き渡し：結果と確認できなかった理由を報告済み
```

一方、「不具合を直し、両条件が通ることを確認する」という依頼なら、この状態では完了にしない。報告したことだけでは、修正や必要な検証の代わりにならない。依頼された確認自体を途中で放棄した場合も、報告を理由に完了へ変えない。

状態を更新する担当は従来どおり、記録ごとに一人。子は自分の範囲を報告し、親は成果物と証拠を受け入れて全体を判断する。子の完了だけでは、統合後の成果物を合格にしない。対象の版や条件が変わったら、過去の結果を残しつつ、影響する範囲の再確認を未着手・未確認として追う。

## 5. OKFは各工程で参照し、引き渡しで保存する

過去の構成や設計理由を知るための検索・参照は、調査・設計など必要な工程で行う。保存は、各工程が渡した候補と根拠を使って、原則として`deliver`が取りまとめる。ここでいう担当工程は仕事上の責任を表し、別のAIを必須にするものではない。

| 工程 | OKFへ残すために渡す情報 |
| --- | --- |
| investigate | 確認できた事実・現在の構成の候補、根拠、未確認の範囲 |
| design | 採用した構成・理由・重要な代替案の採否、採用状況と実装状況 |
| plan | 計画中に確定したシステム上の判断があれば、その候補。作業順序や担当一覧はタスク側に置く |
| implement | 実際に変更した範囲、設計からの差、まだ実装していない範囲 |
| verify・review | 確認した結果、対象の版、証拠、残る問題や限界 |
| deliver | 保存する価値を判断し、重複を確認して保存・更新・関連付け・保存結果の検証を行う |

候補には「何を残すか・対象・理由・根拠・確定度」が分かる短い記述を添え、既存のtask.mdやdesign.mdから渡す。候補台帳や専用ファイルは増やさない。

`deliver`は、実際の操作を[OKFスキル](../../../skills/okf-agent-memory/SKILL.md)の手順で行う。既存の同じ対象の文書を調べ、更新か新規作成かを選ぶ。保存後は内容と形式を確認し、文書の識別子と確認結果をタスク側へ返す。保存方法を各工程へ複製しない。

設計だけで終わる依頼でも、採用が決まった設計はdecisionへ保存できる。その際は「未実装」と記し、現在の構成を説明する文書や、実施済みの歴史にはしない。大規模な仕事では、独立して引き渡せる単位ごとに保存でき、親タスクの完了まで待たせない。同じ知識を扱う複数タスクには保存担当を一人決める。

**system-blueprintの例外：** 現在の構成を説明する文書そのものが依頼された成果物なら、専門スキルが作成中にOKF経由で保存できる。`deliver`は返された文書・対象の版・保存と検証の結果を確認し、同じ内容を再登録しない。文書化を依頼していない通常の調査では、保存候補を渡すにとどめる。

保存に失敗した場合は、保存できた範囲と残る操作を示し、元のタスク記録を保つ。必要な保存が残る依頼は未完了とする。保存候補がない場合は文書を増やさない。読み取り専用の依頼ではタスク・OKFとも書き込まず、結果や候補を回答にまとめる。

## 6. 計画では取得予定を、実行後には証拠を記録する

証拠とは、実際に確認した結果を裏付けるログ・測定値・差分・画像などである。計画工程では、何をどの条件で取得するかを決める。

計画の記入欄を「検証方法」「期待値・合否条件」「必要な証拠」「取得する対象・環境・時点」にする。予定の保存先を記す場合は、未取得であることが分かる表記にし、存在するファイルへのリンクとして扱わない。

| 内容 | 計画時点の記入例 | 実行後の記入例 |
| --- | --- | --- |
| 方法と期待値 | 日付の異なる3件を一覧へ表示し、指定の昇順になることを確かめる | 同じ操作で日付順を比較した |
| 対象・環境・時点 | 実装後の対象版を、テスト環境の固定データで確認する | 確認した版・差分・環境と実行日時を記す |
| 証拠 | 必要な証拠：入力データと実際の並び順。取得予定・未取得 | 実際の並び順と保存できた証拠への参照を記す |
| 判定 | 未確認。実行後に判定する | 得られた結果に基づき合格・不合格・未確認を記す |

計画を作る前に取得済みの基準測定などがあれば、取得した時点と対象を明記して参照できる。その証拠が変更後の状態にも適用できるかは、検証時に判断する。計画は予定を持ち、実行後の結果はtask.mdやverification.mdへ記録して対応付ける。

[verification-template.md](../../../skills/devlow/assets/verification-template.md)は、すでに対象・版・判定・証拠を持つため、その構成を再利用する。実装時に用語と参照の整合を確認する。

共通規則はworkflow.mdに集め、各工程とテンプレートは参照する。実装時は[全体設計資料](../../devlow-design.md)と[タスク管理の一覧](task-management-inventory.md)の該当説明も合わせ、[実装・確認記録](implementation.md)へ実施範囲を追記する。基本の配置・配布方針は[architecture.md](../../architecture.md)を維持する。

### 利用先で残す記録

次のパスは利用先プロジェクトからの相対パス。既存の同じタスク・同じ知識があればその記録を優先する。記載した名前のファイルを毎回すべて作るわけではない。

`<task-id>`は仕事の識別名、`<system>`は対象システムの名前、`<decision>`と`<event>`は判断や出来事の識別名に置き換える。例えば`.space/tasks/list-order-check/task.md`は、一覧の並び順を確認する仕事の記録になる。

| 保存先の例 | 作成する条件と内容 |
| --- | --- |
| `.space/tasks/<task-id>/task.md` | 標準・大規模で作成。依頼の終了条件、進行状態、成果判定、工程と詳細への参照 |
| 同じ場所の`design.md`・`plan.md` | 独立した設計・計画が必要な場合。大規模の親は独立したplan.mdを持つ |
| 同じ場所の`verification.md`・`review.md`・`evidence/` | 確認結果や証拠を分けて扱う必要がある場合。短ければtask.mdにまとめる |
| `.space/babel/decisions/systems/<system>/<decision>.md` | 保存対象に選んだ設計と理由。採用状況と実装状況を明記 |
| `.space/babel/knowledge/systems/<system>/blueprint.md` | 確認できた現在の構成を文書化する場合 |
| `.space/babel/knowledge/systems/<system>/history/<event>.md` | 重要な変更・障害・復旧・撤回等の確定した経緯と結果を残す場合 |

小規模な会話中の依頼にはtask.mdを新規作成しないが、状態と判定の区別は同じように回答へ適用する。読み取り専用なら規模を問わずファイルを作成しない。タスク管理CLIを使う場合は進行状態の正本を台帳にし、task.mdから参照する。本設計ではCLIの保存形式、状態の内部コード、TSVは定義しない。

中断からの再開に必要な要約は、従来どおり[checkpoint-safely](../../../skills/checkpoint-safely/SKILL.md)に任せる。工程終了のたびにcheckpointを作る運用は追加しない。

## 8. 実装の順序と完了の確認

一人の修正担当が、まずworkflow.mdの共通規則を更新し、次にtask-template.md、各工程、計画テンプレートへ反映する。最後に開発資料の説明をそろえる。途中の状態を完成版として扱わず、次の例が図・本文・ひな形のすべてで一致することを確認する。

| 確認する例 | 期待する動作 |
| --- | --- |
| レビューだけで問題を発見 | 検証工程を先行必須にせず、指摘を報告して終了。依頼外の修正へ進まない |
| 検証だけで不合格、または報告範囲に含まれる確認不能 | 依頼は報告完了、対象は不合格・未確認として別々に残る |
| 修正と検証まで依頼され、必須条件が不合格 | 修正可能な範囲へ戻るか、必要な前提を待つ。報告だけで完了にしない |
| 検証済みの変更で独立レビューが不要 | 検証から引き渡しへ進む |
| 未着手・省略・再利用の工程 | 実行状態と確認結果を区別し、省略を合格・完了に数えない |
| 設計採用後、実装前に終了 | deliverで必要なdecisionを未実装として保存。現在の構成・実施済みの歴史にはしない |
| blueprintが文書を保存済み | deliverが結果を確認し、重複保存しない |
| 計画に取得予定のログを記入 | 取得済みの証拠として扱わず、実行後の結果へ対応付ける |
| 子が完了、統合した成果物は未確認 | 親の全体完了・対象合格へ自動で置き換えない |
| 必要なOKF保存に失敗 | 保存の未完了と成果物の完成を分け、元の記録を保持する |

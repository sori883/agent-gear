# orchの設計：unitを分担し、結果を確認して引き渡す

2026-09-23作成。レビュー修正を採用して実装へ進む設計。現在の実装・検証範囲は[実装記録](../orch/implementation.md)を参照する。この文書は会話を読んでいない人向けに、利用方法、管理する情報、ファイル、実装する範囲を説明する。コマンドの詳細は[CLIの設計案](orchestrator-cli-design.md)を参照する。

既存の方針は[配布設計](../../architecture.md)と[全体フロー](../../../skills/devlow/references/workflow.md)。ここで比較した保存方式・コマンド構成の推奨案を採用し、orchの配布用ソースに実装した。利用時の具体的な入力は[CLI仕様](../../../skills/orch/references/cli.md)を参照する。

## 1. 何を解決するか

複数のエージェントで作業すると、作業完了の報告、確認済みの証拠、判断待ちが別々の会話に残る。親が会話を読み直して状態を復元しなくても、何を依頼し、何が返り、何を確認して次へ進めたかを追えるようにする。

orchは二つからなる。**スキルは親・子の動き方を定め、CLIは管理情報を保存・照合する。** エージェントの起動・待機・停止は利用環境の道具を親が操作する。CLIはエージェントを起動せず、コードの実装、テスト実行、PR操作、OKFへの保存もしない。

導入するのは大規模の分担作業と、依存・担当交代の管理が必要な中規模作業。単独の小規模依頼には台帳を作らない。並列実行できない環境でも、同じunitを順次進められる。

## 2. task・unit・工程の関係

| 用語 | 意味 |
| --- | --- |
| タスク | 利用者に説明する仕事のまとまり。目的・範囲・完了条件を持つ |
| unit | CLIに登録して、担当・状態・受け入れを追う作業単位。登録したタスクを指す管理上の名前 |
| 親unit | 複数の子unitを束ね、共通計画と統合後の結果を管理するunit |
| 工程 | intake・design・implement等、そのunitの中で行う仕事の種類 |
| 試行 `attempt` | 担当交代ややり直しを区別する番号。古い担当の報告を現在の作業へ混ぜないために使う |
| 受け入れ | 親が報告・成果物・証拠を確認し、依頼した範囲が終了したと判断すること |

CLIで扱う親・子はどちらもunitとし、別のprogramという管理階層は作らない。既存のtask IDをunit IDとして使い、同じ仕事に二つのIDを付けない。一つのunitは複数工程を通れる。工程、ファイル、エージェント、PRの数から自動的にunitを増やさない。

分ける目安は「成果物と完了条件を独立して確認でき、担当範囲や着手条件を分ける必要があること」。同じ目的の短い手順は、unit内の計画項目にする。

| 規模・役割 | task.md |
| --- | --- |
| CLIを使わない小規模依頼 | 新規作成しない |
| 台帳に登録する小規模な子unit | 新規作成しない。台帳に短い目的・完了条件・報告を持つ |
| 中規模以上のunit | `.space/tasks/<unit-id>/task.md`を持つ。既存の記録先があれば参照する |
| 大規模の親unit | task.mdと独立したplan.mdを持ち、子の文書を参照する |

task.mdは担当エージェントが既存のひな形から作成する。CLIは本文を生成・上書きせず、参照を登録する。CLI利用時は状態の欄を台帳参照へ置き換え、手書きの最新状態を二重に管理しない。

## 3. 親・子・CLIの責任

| 担当 | 責任 |
| --- | --- |
| 親・統括担当 | 分割、共通条件、依存関係、所有範囲、担当の割当、子の起動、受け入れ確認、統合と全体の引き渡し |
| 子・作業担当 | 自分のunitの工程選択・進捗、成果物、確認結果、未決事項、完了または未完了の報告 |
| CLI | 入力検査、担当と試行の照合、状態の保存、循環依存の検出、着手候補・未処理報告・判断待ちの表示 |

親と子が同じ進捗欄を書き換えない。親は別の受け入れ記録を更新し、差し戻された子が自分の作業を再開する。小規模な子の記録を親が代行する場合は、登録時に記録担当を親として明示し、作業担当からの報告を根拠に更新する。

担当IDは引き継ぐ役割を識別する名前とし、実際に動くセッションと試行番号を別に記録する。同じ親が統括と実作業を兼ねてもよい。担当交代では旧担当の書き込み終了を確認し、セッションと試行番号を変える。CLIの担当照合は同じプロジェクト内の誤更新を防ぐ仕組みであり、利用環境の権限管理の代わりにはしない。

## 4. 一回の運用例

例は「メール通知とアプリ内通知を追加する」という依頼。親は全体の条件、子は個別の通知の成果物を持つ。

1. intake・design・planで依頼範囲、共通設計、必要な子unitを決める。orchの導入は第9の工程を追加することではない。
2. 親が台帳を初期化し、親unitと子unitを登録する。中規模以上の文書を用意し、担当・依存・必要な確認条件を設定する。
3. 親が着手候補を確認する。CLIに記録された条件に加え、実際の作業環境、権限、共有ファイルの競合がないことを確認して担当を起動する。
4. 子は自分のunitを開始し、必要な工程を進める。状態や次の判断が変わる節目に台帳を更新する。
5. 子が成果物の版、確認結果、報告を提出する。CLIは作業完了と報告通知を一度の更新で保存する。
6. 親が未処理の報告を読み、実物と証拠を確認して受け入れるか差し戻す。通知を読んだだけでは受け入れ済みにしない。
7. 最初の子を引き渡しまで通した結果から、指示や確認条件を補正し、残りのunitへ展開する。
8. 子がそろった後、親が統合後の結果を確認する。deliverが必要な納品・OKF保存を行い、親unitを終了する。

質問が必要になった場合はgateへ記録し、親が人間へ質問する。回答が必要なunitだけを待ちにし、独立した作業は続ける。gateに既定案があっても、回答や承認の代用にはしない。

## 5. 三つの状態を分ける

| 軸 | 値 | 更新担当 |
| --- | --- | --- |
| 作業の進行 | `pending`未着手、`running`実行中、`waiting`判断・前提待ち、`paused`中断、`completed`完了、`cancelled`中止 | unitの記録担当 |
| 条件ごとの成果判定 | `pass`合格、`fail`不合格、`unknown`未確認、`not-applicable`対象外 | 確認を担当したエージェント。代理記録なら実施者も残す |
| 提出物の受け入れ | `pending`未確認、`accepted`受け入れ済み、`changes-requested`差し戻し | 親。親を持たないunitは統括担当 |

例えばレビューだけの依頼は「作業はcompleted・対象の判定はfail・報告はaccepted」が成立する。報告を受け入れたことは、対象コードの合格を意味しない。

完了条件には「依頼を終了するための条件」と「対象を評価する条件」を区別してIDを付ける。レビュー依頼なら前者は指摘・根拠・確認限界の報告、後者は対象コードの品質条件である。修正まで依頼されたunitでは、必要な修正・検証の合格も終了条件に含める。

CLIは、終了に必要と登録された条件の判定がそろっていることを検査する。条件の内容や証拠の十分さを読んで判断するのは担当と親であり、ファイルが存在するだけでは合格にならない。判定を一つの総合合否へ潰さず、条件別に表示する。

親の完了は子の件数から自動判定しない。現在の子の提出が受け入れられ、親自身の統合・納品条件が満たされたことを確認する。中止した子がある場合は、範囲変更の理由と、元の条件をどこで扱ったかも親が記録する。

## 6. 依存と再確認

依存は「Bを始めるにはAのどの結果が必要か」を持つ。既定はAの現在の提出が受け入れ済みであること。コードの合格も必要なら、依存に必要な条件IDと期待する判定を追加する。これにより、不合格を報告しただけのレビューunitが、修正完了の前提と誤認されることを防ぐ。

存在しない参照、自己依存、循環を登録時に拒否する。親が子の終了を待つ関係も含めて循環を確認し、子が親の完了を待つ構成を許さない。未マージの変更を使えるか、作業環境へその変更が届いているかは親が確認する。

着手時には使った依存先の提出ID・成果物の版を保存する。依存先のやり直し、条件変更、成果物更新でその前提が変わったら、後続を「前提の再確認が必要」と表示する。後続の既存の作業状態や証拠を消さず、現在の受け入れを有効とは扱わない。この確認は、親の統合結果やさらに依存するunitにも伝える。同じ試行でのstartは契約・入力が変わらない再開に限る。前提変更時はreopenで新試行へ進み、照合した証拠だけを新たに記録する。旧提出と未処理通知は現在無効として履歴に残す。新しい提出には、置き換え済みではない現在有効な確認記録だけを使う。

`ready`は記録上の着手候補であり、自動起動の指示ではない。未解決gate、未確定の条件、必要な文書・担当の不足、満たされない依存を理由付きで表示する。

## 7. ファイルと正本

推奨配置は次のとおり。利用先プロジェクトに作るファイルであり、配布元へ保存しない。orchの起動は`--store`で台帳を明示する。初期化時に対象プロジェクトを結び付け、カレントディレクトリだけから別の台帳を自動作成しない。

```text
.space/
├── tasks/
│   ├── .orch/
│   │   ├── state.json             管理情報の正本
│   │   └── exports/               必要時にexportで生成する参照用の出力
│   │       └── <revision>/
│   │           ├── units.tsv      unitの一覧
│   │           ├── ledger.tsv     条件ごとの確認結果
│   │           └── status.md      親子関係・進捗・未確認・判断待ち
│   ├── notification/
│   │   ├── task.md                親の目的・条件・資料への入口
│   │   └── plan.md                共通設計への参照・分担・統合計画
│   ├── email-notification/
│   │   ├── task.md
│   │   └── verification.md        詳細が必要な場合だけ分割
│   └── in-app-notification/
│       └── task.md
├── checkpoint/                    checkpoint-safelyが作成・更新
└── babel/                         deliverからOKFスキルへ保存を依頼
```

TSVは作成できるが、推奨案では書き換える台帳ではなく、ある時点の出力とする。出力には台帳のrevisionと日時を付ける。`status`は読み取り専用で、ファイルを残すときだけ`export`する。過去の出力を最新状態として読み戻さない。

| 情報 | 正本 |
| --- | --- |
| ID、親子、担当、依存、工程の選択・状態、確認結果、報告・受け入れ、gate | state.json。CLI経由で操作 |
| 依頼の説明、設計の内容、計画の詳細、実際の証拠 | task.mdと必要な成果物。担当が更新し、台帳から参照 |
| 人間が一覧で確認・共有する表 | exportのTSV・Markdown。生成物として扱う |
| 再開の要約 | checkpoint。保存時点の参照を持つ |
| 確定したシステムの設計・判断理由・歴史 | OKF。台帳の履歴は丸ごと移さない |

条件の説明文はtask.md等、CLIが検査する条件ID・必須性・期待判定は台帳に置く。変更時は親が両者の一致を確認して条件の版を更新する。CLIの利用を始めた後、task.mdの工程表には台帳参照と選択理由を残し、同じ実行状態・合否を手書きで維持しない。

## 8. 保存方式の比較と推奨

| 案 | 利点 | 費用・制約 |
| --- | --- | --- |
| A：複数のTSV・JSON・Markdownをそれぞれ正本にする | pstackに近く、ファイルごとに直接読める | 作業完了・報告通知・受け入れ等を複数ファイルへ保存する際、途中失敗の復旧規則が必要 |
| B：一つのJSONを正本にし、TSV等を出力する | 一操作の結果をまとめて確定でき、条件別判定・親子・報告を同じ版で照合できる | 更新時に台帳全体を読む。TSVは現在状態の正本にならない |

**初版はBを採用した。** 複数担当による更新と、提出・通知の整合性を優先する。Aから、人間が一覧を読めるTSV出力を取り込む。本文やテストログはJSONに埋め込まず、参照と管理に必要な短い説明だけを保存する。

初版は同じホストからローカルの一つの台帳を利用する。複数worktreeでも親が同じ台帳の場所とプロジェクト基準の参照を渡す。ホスト間の共有やネットワークファイルシステム、非常に大量のunitを扱う用途は対応済みとしない。実運用で容量・更新時間を測り、必要なら保存方式を見直す。

## 9. スキルと実装の配置案

| ファイル | 所有する内容 |
| --- | --- |
| `skills/devlow/references/workflow.md` | 全体の工程と、orchを使う条件・接続先 |
| `skills/devlow/references/orchestrate.md` | 計画から分担へ渡す入力、結果をverify・review・deliverへ戻す接続。従来のprogram.mdという予定名を置き換えた |
| `skills/orch/SKILL.md` | unit管理スキルの入口 |
| `skills/orch/references/orchestration.md` | 親・子の運用手順、更新責任、質問・差し戻し・再開 |
| `skills/orch/references/cli.md` | コマンド、状態、保存・復旧の操作仕様 |
| `skills/orch/scripts/task.ts` | CLIの入口。配布設計で定めたtask.tsを維持 |
| `skills/orch/scripts/bootstrap.ts`、`lib/`、`package.json` | 初回準備、処理本体、スキル内で完結する実行環境。外部依存を追加する場合は同じscripts内にbun.lockも置く |
| `skills/orch/tests/` | 状態・依存・保存失敗・実CLIの検証。配布対象外 |

`orch`はスキルと利用時の呼び名とする。資料中の`orch ...`は`bun <配布されたorchスキル>/scripts/task.ts ...`の略記であり、グローバルコマンドの導入を前提にしない。別のトップレベルCLIや同じ責務のtask-managementスキルは増やさない。

初版の実装はBunと標準APIを基本とし、外部サービス・Graphite・常駐プロセスを必須にしない。配布後もTypeScriptで実行し、依存を利用先プロジェクトのpackage.jsonへ追加しない。

## 10. 初版の範囲と実装順

初版にはunit登録、依存、担当・状態、条件別の確認記録、提出・受け入れ、報告受信、判断待ち、一覧とTSV出力を含める。Graphiteのfrontier、standing専用コマンド、自動マージ、エージェント自動起動は含めない。共通指示は親のtask.md・plan.mdを参照する。

| 順序 | 作るもの | 完了を確かめる例 |
| --- | --- | --- |
| 1 | 親子の運用手順とCLI契約 | 小規模の子にtask.mdを増やさず、報告と受け入れの担当が一意になる |
| 2 | 保存層、unit、担当・試行、一覧 | 並行更新で他unitを消さない。古い担当の更新、無効な遷移を拒否する |
| 3 | 依存・工程・条件・ledger | 循環を拒否する。以前の版の合格を現在の版へ流用しない |
| 4 | 提出・受け入れ・inbox・gate | 提出と通知が一緒に保存され、読み取り後に親が止まっても報告を失わない |
| 5 | status・exportと配布先での起動 | 同じrevisionのTSVとMarkdownを生成し、配布元への参照なしで実行できる |
| 6 | 全体フローとの接続と実運用 | 一つの子を引き渡しまで通し、指示・文書・台帳のずれを修正する |

実装時は変更する観測可能な振る舞いを先にテストで示し、対応する処理を追加する。対象テストの予定は`bun test skills/orch/tests`。実コマンドはリポジトリ外へコピーしたスキルでも確認し、初回導入・再起動・依存更新、利用先への保存を確かめる。これらは検証計画であり、実行済みの証拠ではない。

### 受け入れシナリオ

| シナリオ | 必要な結果 |
| --- | --- |
| 中規模の単独作業 | 一つのtask.mdで複数工程を進め、台帳と状態を二重管理しない |
| 大規模内の小規模な子 | unitを登録でき、独立task.mdは不要 |
| レビューのみで不具合を発見 | completed・fail・acceptedを区別して保持し、依頼外の修正へ進まない |
| 修正・検証を依頼されたがテストが失敗 | 必須の合格条件が満たされず、提出完了・全体完了にできない |
| 子は完了したが親は未確認 | 子の完了件数と受け入れ件数を別表示し、後続を自動解放しない |
| 設計文書を変更して再提出 | PRがなくても版を識別でき、旧版の確認・受け入れは現在に適用しない |
| 判断待ちが一つある | 関係するunitだけが候補から外れ、回答前に既定案を実行しない |
| 親が報告を読んだ後に停止 | 報告は未処理として残り、再開後に確認・処理できる |
| 保存中に停止、または並行更新 | 正本は変更前か変更後の有効な状態。部分更新や成功扱いの未保存を生じさせない |

## 11. 既存資料への反映と未決事項

設計の承認後、orchスキル・CLIと全体フローへの接続を実装した。テスト結果とリポジトリ外での動作確認は[実装記録](../orch/implementation.md)に残す。配布生成と利用環境へのインストールは別の作業とする。

全体設計のtask-managementという仮称、program.mdという予定名、タスク管理一覧を更新し、全体フローとtask-templateにCLI利用時の参照方式を具体化した。設計理由やpstackとの差、開発時の確認記録はdocsに置き、配布用資料には利用者・実行AIが必要な仕様だけを書く。

既存task.mdは自動移動・削除しない。移行する単位のID・条件・参照を親が確認して登録し、その時点から進捗の正本を切り替える。CLI利用をやめる場合も同じ時点のexportを参照し、文書へ管理を戻す範囲を明示する。古い文書をそのまま最新状態として再利用しない。

今回採用した判断は、orchというスキル名、taskとunitの対応、JSONの正本とTSV出力、破壊的な受信操作を使わないこと、初版から依存と受け入れを持つこと。CLI入力形式は配布用cli.md、schemaVersion 1の型と実行時検査はscripts/libに具体化した。外部依存が空の場合のbootstrapを配布設計に明記した。保存の動作確認は今回の実行環境で行い、他OS・ネットワーク共有・電源断の保証には広げない。

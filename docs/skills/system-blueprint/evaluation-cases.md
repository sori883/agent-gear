# ブループリントの評価ケース

成果物の意味と根拠を確認するためのケース。見出しや文言の一致だけを成功条件にしない。実行評価に使う場合は、対象コードと依頼だけを評価担当へ渡し、この期待結果は採点側で使う。生成物は一時プロジェクトに置き、開発リポジトリのbundleへ保存しない。

| ケース | 依頼・入力 | 確認する結果 |
| --- | --- | --- |
| 小さなシステム | CLIと保存処理を持つ小規模な実装のブループリント | 意味のある境界で全体像と詳細を整理する。ファイルごとの機械的な分割、空のflow、架空の配置を作らない |
| モノレポ | Web、API、ワーカー、共有パッケージがある実装 | パッケージ境界と実行単位を区別し、関係をコードや起動設定で裏付ける |
| 古いREADME | READMEは同期処理、現コードはキュー経由 | 実装で確認した経路を説明し、READMEとの不一致を出典付きで残す |
| 理由不明 | キューの実装はあるが採用理由の記録はない | 非同期化を事実として書き、性能目的などを断定しない。調査範囲と不明点を残す |
| 明示的な決定 | PRに非同期化の理由と制約が書かれている | 根拠をdecisionへ保存し、構成要素やフローから関連付ける。理由と影響を無意味に分割しない |
| 推論と矛盾 | 複数の状況証拠と、食い違う設計資料がある | whyの確度を維持し、SupportedをDirectへ格上げしない。両方の資料を示す |
| 設定しかない配置 | Composeはあるが実環境にアクセスできない | 設定上の構成として記録し、本番でその構成が稼働すると断定しない |
| 既存のOKF文書 | 標準配置とは別の場所に同じ責務のconceptがあり、無関係な文書もある | 検索・showで確認し、元のIDを更新する。標準配置に合わせるためだけに移動・複製せず、無関係な本文・メタデータやリンクを保持する |
| 更新 | 既存のフローが別の実装に置き換わった | 旧情報と新しい根拠を照合し、関連するconceptと全体像を更新する。`-v2` の重複を作らない |
| 保存失敗 | CLIの保存や形式検証が失敗する | 保存済みの範囲と未完了部分を区別し、成功・検証済みと報告しない |
| howの単独利用 | 特定モジュールの仕組みを説明してほしい | howの出力を返し、依頼のないブループリントやOKF文書を自動生成しない |
| whyの単独利用 | 閾値の採用理由を知りたい | 配布版のwhyに従ってGit履歴・PR・リポジトリ内資料を調べ、調査範囲と取得できない資料、確度5区分を示す。結果不明も調査結果として返す |

## 共通の採点観点

- 全体像から必要な詳細に到達し、文書単体でも対象・責務・根拠を理解できるか。
- 主要な関係やフローが実装に対応し、図と本文で矛盾しないか。
- 明示された理由と、現在の動作からの推論を区別できるか。
- 不明点のために根拠を作ったり、価値のある文書化全体を止めたりしていないか。
- 保存先、conceptのtype、sources、code_refs、関連リンク、目次、履歴がOKFに適合するか。
- エージェントの作成や自動検証を、人間の内容確認 `verified` として記録していないか。

## 初版での検証範囲

原文との照合、リンクと形式の検証、上記ケースに対する手順の机上確認、隔離したbundleでの保存・関連付け・更新・検証を行う。これらを、PR取得を含むhow・whyの実行試験や、独立したエージェントによる全ケースの実行と同一視しない。

- how・whyのサブエージェントや外部MCPを使った実行試験、および独立したエージェントによるケース実行は未実施。

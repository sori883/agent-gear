# 配布・導入の実装と確認結果

2026-09-23。ユーザーが承認した、AIで実行できる残作業を実施した。[設計](distribution-design.md)に従い、配布生成、setup、カタログ、CI定義、OKFの依存移行、実際の子担当によるorch利用と短時間の容量測定を完了した。CodexとClaude Codeへagent-gear 0.1.0+codex.20260923104742をローカル導入済み。remoteへのpush・mainへのmerge・公開は行っていない。

## できたこと

buildはskills・space・packagingの許可した構成だけから両製品を生成する。各製品115ファイル、カタログ2ファイルの計232ファイルで、9スキルを同梱する。TypeScriptのまま配布し、docs・開発用テスト・node_modules・開発リポジトリの.spaceを取り込まない。再生成検査は内容と全パスを比較し、未追跡の追加ファイルも検出する。

OKFの依存をscripts内へ移した。初回・lock変更・依存欠落時の固定導入、同時起動、失敗時の停止を確認した。同時起動で別プロセスの導入を待った場合にも再起動が必要と分かり、OKFとorchのbootstrapを修正した。詳しくは[移行記録](skills/okf-agent-memory/runtime-migration.md)を参照する。

setupは既存の指示の管理ブロック外と独自知識を保持する。全件の事前照合、plugin単位の排他、pending記録からの再開を実装した。最初の提出では両製品の共有vendor更新が衝突して止まることを統合確認と独立検証で発見し、差し戻した。現在の内容が新版の配布内容と完全一致する場合は管理記録を更新し、異なるローカル編集は引き続き保護する。[setupの実装記録](skills/setup/implementation.md)に根拠を残す。

共通知識は旧.space/babelから23原則と利用に必要な目次・LICENSEをspace/babelへコピーして正本化し、frontmatterの末尾空白を整えた。旧ファイルは削除していない。本文がTODOだけの承認ルール草案と開発時の操作履歴は配布しない。旧templates/AGENTS.mdも保持するが、配布用指示は製品別のpackagingに置いた。開発用.codex/agentsは製品へ含めていない。

## orchを実際の分担に使った結果

親unit `agent-gear-rollout`の下で、三つの実際の子エージェントが自身の開始・工程更新・確認記録・提出をCLIへ保存した。親は成果物・生の実行記録・現在のハッシュを確認して受け入れた。台帳は`.space/tasks/agent-gear-rollout/orch/`、途中の証拠は対応するtaskディレクトリに保存し、配布物には含めていない。

| unit | 実施した仕事 | 受け入れ対象 |
| --- | --- | --- |
| okf-runtime | OKFの実行依存移行 | 試行1、提出a6e6b706-5d5d-4e89-86b4-361608e62817 |
| project-setup | setupの実装と統合指摘の修正 | 試行2、提出027e7beb-635d-4d00-871b-5a64ef2b324b |
| orch-operations | 負荷測定と保持・切り替え方法 | 試行1、提出c64d2b69-469c-4425-b7e9-a0b1cee7ca2c |

setupでは初回提出をreturnし、子がreopenして試行2へ進み、新たな検証記録で再提出した。旧提出と通知は履歴として保持され、現在の受け入れと混同されなかった。子の状態を親が直接書き換える運用はしていない。CLI自体が子エージェントを起動・停止したという意味ではない。

短時間の負荷測定では300子unit＋親1、331試行、1,158操作でstateは3.62 MiB。status中央値61.1 ms、工程更新64.1 msだった。6プロセスの同時報告も、ロック競合への有限再試行後に各一回保存された。[運用資料と機械可読の結果](skills/orch/operations.md)に条件・限界・保持方針を記録する。

# agent-gearの目的と配布設計

agent-gearは、AIエージェントが開発で使うスキル・CLI・共通知識・ルールを、CodexとClaude Code向けに配布するためのリポジトリである。利用先のプロジェクトで、知識管理、タスク分割・管理、必要な文書や設定の導入を行える道具を作る。

**スキルごとにCLIと実行時の依存関係を持たせ、Codex・Claude Code向けの配布物を `main` ブランチで管理する。CLIは配布後もTypeScriptとし、Bunで実行する。**

この文書を、何を作るか・どこに置くか・どう配布するかを判断するための設計方針の正本とする。以下は目標の構成であり、すべてが実装済みという意味ではない。実装状況や検証結果は [現状資料](current-state.md) や個別の開発資料に記録し、この設計と区別する。

## 製品と開発環境を区別する

このリポジトリで開発するのは、別のプロジェクトへ配布して使う道具である。開発リポジトリ内だけで動くことを完成条件にしない。配布元への絶対パス、配布元の依存パッケージ、配布物に含まれないファイルへのリンクに依存させない。

リポジトリ内のスキル・エージェント定義・ルール・原則・指示テンプレートは開発対象であり、その指示をこのリポジトリでの作業ルールとして適用しない。開発時の指示はルートの [AGENTS.md](../AGENTS.md) とユーザーの指示に従う。

配布物には、その配布物を保守する人向けの記述を一切含めない。配布するスキル本文・参照資料・プロンプト・テンプレート等には、利用者または利用先で実行するAIに必要な内容だけを記載する。保守方針、原版との差分、変更経緯、開発時の検証記録などは、配布対象外の `docs/` 等で管理する。

`ai-dev-tools` などのプラグイン名は構成例であり、正式名称は別途決める。この文書を理由に、既存のスキル名やリポジトリ名を一律に変更しない。

## 正本・配布物・利用先

配布用の正本は `skills/`・`space/`・`packaging/` に置く。生成した配布物と、利用先へ配置したコピーはそれぞれ区別する。

| 場所 | 役割・管理方針 |
| --- | --- |
| `skills/` | 配布するスキルと専用CLIの正本。スキル専用の説明・実行手順は `references/`、実行コードと依存定義は `scripts/`、開発用テストは `tests/` に置く |
| `space/babel/` | 配布する共通知識・ルールの正本。複数のスキルやエージェントから参照する文書を置く |
| `packaging/codex/`・`packaging/claude-code/` | 製品別のマニフェスト、エージェント定義、必要なhooksや指示テンプレートの正本 |
| `scripts/build.ts` | 共通ソースと製品別定義から、配布物とカタログを生成する開発用の入口 |
| `dist/<製品>/<plugin-name>/` | 自動生成した配布物。Gitで管理し、手編集しない |
| ルートの `package.json`・`bun.lock` | 配布物の生成、リポジトリ全体の検証に使う開発依存と、配布物のリリース版数を管理する |
| `docs/` | 開発者向けの目的・設計・実装状況・検証記録。配布対象に含めない |
| 開発リポジトリ自身の `.space/` | このリポジトリで利用する知識と作業記録。配布物の生成対象に含めない |

共通知識の本文を `space/babel/` と各スキルの `references/` に重複して管理しない。共通文書を修正するときは `space/babel/` を変更し、配布物と利用先のコピーへ反映する。

## 全体フローと工程の定義

開発作業の全体フローは、統括スキルに同梱する `skills/development-workflow/references/workflow.md` を正本とする。工程の順序・分岐、各工程の成果物と完了条件、依頼種別・作業規模・リスクによる実施判断を定義する。判断や設計は、小規模な作業でもなるべく記録に残す。

統括スキルの `SKILL.md` は同梱する全体フローを相対参照し、今回の工程を選択して実行する。各工程の具体的な実行手順は担当するスキルとその `references/` に置き、全体フローの本文を複製しない。タスクの成果物は利用先へ保存し、配布用ソースと分ける。

全体フローは、統括スキルが所有する実行手順としてスキルと一緒に配布・更新する。複数工程が参照するという理由だけでBabelの共通知識にせず、フローの読込にsetupやOKFを必要としない。複数の独立したスキルから使う原則・ルール等は引き続きBabelに置く。

checkpointの作成・更新・保存には [checkpoint-safely](../skills/checkpoint-safely/SKILL.md) を使う。保存先、記録形式、ひな形、保存・中断の手順は同スキルが所有する。全体フローは保存するタイミングと渡す情報を定義し、返された記録への参照を保持する。統括スキルやタスク管理CLIにcheckpointの保存手順を複製しない。

具体的なスキル構成、工程ファイル、成果物の分割、規模ごとの選択は[開発フローの設計案](development-workflow-design.md)で検討する。この設計案にある新規ファイルやタスク管理CLIは未実装であり、ここに記載した配置方針と実装状況を区別する。

## CLIと依存関係はスキル単位にする

共通のトップレベルCLIは作らない。次の責務を別のスキルとCLIで提供する。

| 責務 | CLIの入口 | 提供するもの |
| --- | --- | --- |
| OKF | `scripts/okf.ts` | frontmatter付きMarkdownの知識を検索・保存・更新・検証する |
| タスク分割・管理 | `scripts/task.ts` | タスクを分割し、その状態を管理する。保存形式・具体的な配置名は別途設計する |
| 初期配置・更新 | `scripts/setup.ts` | 同梱する共通文書・エージェント定義・指示テンプレートを利用先へ配置・更新する |

各CLIの入口、`bootstrap.ts`、処理本体の `lib/`、実行時の `package.json` と `bun.lock` は、すべて `skills/<skill-name>/scripts/` に置く。実行時に生成する `node_modules/` も同じ `scripts/` 配下に置く。

ルートの依存関係がなくても、スキル単体で動く構成にする。利用先プロジェクトの `package.json`・`bun.lock`・`node_modules/` に、スキルの依存関係を混ぜない。

起動時は、外部ライブラリに依存しない `bootstrap.ts` が導入状態と依存定義・ロックファイルのハッシュを確認する。初回や変更時には自身の `scripts/` で `bun install --frozen-lockfile` を実行し、成功後にハッシュを保存してCLIを再起動する。その後、処理本体を動的に読み込む。導入に失敗した場合は、本体を実行せずエラーを返す。

プラグインをインストールしただけで、スキルの依存関係も自動導入されるとは扱わない。実行にはBunとスキルの `scripts/` への書き込み権限が必要になる。依存導入先はスクリプト自身の位置から決め、本体は呼び出し元の作業ディレクトリを保つ。知識やタスク情報などの成果物は、利用先プロジェクトに保存する。

## 共通知識とプロジェクト固有の記録

`space/` は配布用ソース、`.space/` は各プロジェクトでの利用場所という、本プロジェクト独自の名前分けである。OKFや配布先製品が要求する名前として扱わない。

| データ | 保存先 |
| --- | --- |
| 配布する共通知識・ルールの正本 | 開発リポジトリの `space/babel/` |
| setupが配置・更新する共通文書 | 利用先の `.space/babel/vendor/<plugin-name>/` |
| プロジェクト固有の知識・ルール・設計判断 | そのプロジェクトの `.space/babel/` 直下のtype別ディレクトリ |
| タスク単位の作業記録・再開情報 | そのプロジェクトの `.space/checkpoint/`。ファイル名と既存記録の扱いはcheckpoint-safelyで定義する |

Babelの文書はfrontmatter付きMarkdownとし、配布元・利用先とも同じ分類を使う。

| `type` | ディレクトリ |
| --- | --- |
| `rule` | `rules/` |
| `principle` | `principles/` |
| `knowledge` | `knowledge/` |
| `procedure` | `procedures/` |
| `decision` | `decisions/` |

system-blueprintが新規に作成する構成・動作の説明は、利用先の `.space/babel/knowledge/systems/<system>/` に保存し、全体像の入口を `blueprint.md` とする。根拠のある設計判断は `.space/babel/decisions/systems/<system>/` に保存する。対象システムごとに安定して参照・更新できるよう、単一システムでも `<system>` を省略しない。詳細の配置は配布用の[文書モデル](../skills/system-blueprint/references/document-model.md)で定義する。

これらのファイルはOKFスキルのCLIで作成・更新し、bundleは `.space/babel/` のまま、concept IDで保存先を指定する。既存の同じ対象・責務の文書は元のIDで更新・参照し、標準配置に合わせるためだけに移動・複製しない。この方針は新規生成先の明確化であり、既存文書の一括移行は含まない。

system-blueprintはブループリント固有の保存先・concept ID・typeを定義する。CLIの準備、コマンド書式・引数、作成・更新・関連付け・形式検証の実行方法はOKFスキルを正本とし、system-blueprintに実行例や操作手順を複製しない。

how・whyにも、OKFスキルによる既存知識の検索・参照を明記する。howは構成・動作の説明を現在のコード・設定と照合し、whyは決定・制約・経緯を採用理由の根拠として評価する。両者は読み取り専用とし、bundleの初期化や知識の保存・更新は行わない。確認済みの知識・検索範囲・不足を担当間で引き継ぎ、CLIの実行手順は複製しない。

whyはGit履歴・PR・コードコメント・テスト・リポジトリ内の資料から設計理由を調べる。配布内容に関するプロジェクトの制約により、外部の課題管理・文書・チャット・監視・分析サービスを探索する専用手順は含めない。担当分担と出力形式もこの調査範囲に合わせ、原版の情報源カテゴリを網羅する指示は引き継がない。根拠と確度の区別、矛盾や不明点の報告は維持する。

checkpointは作業の現在状態と再開に必要な情報を残す。必要な記録項目とGitへの保存条件はcheckpoint-safelyを正本とする。別の作業でも使う知識や決定は、プロジェクトのBabelへ整理する。checkpointはOKFの検索・形式検証と配布の対象に含めない。

## setupと製品別の配置

setupは、プラグイン自身の位置から同梱ファイルを読み、利用先プロジェクトへ配置する。プラグインの更新と、プロジェクト内の文書・設定の更新は別の処理として扱う。

| 配布するもの | 利用先での扱い |
| --- | --- |
| 共通知識・ルール | `.space/babel/vendor/<plugin-name>/` に配置し、目次・5種類のディレクトリ・文書間リンクを保持する |
| Codex向けエージェント定義 | 配布物の `templates/agents/` に同梱し、必要に応じて `.codex/agents/` へ配置する |
| Claude Code向けエージェント定義 | 配布物の `agents/` に同梱し、プラグインのエージェントとして提供する |
| `AGENTS.md`・`CLAUDE.md` のテンプレート | 既存の指示を確認して統合する。配布用テンプレートと開発リポジトリの指示を混同しない |
| hooks | 使用する場合にだけ、配布先製品の形式で組み込む |

更新対象は、そのプラグインが管理するファイルに限る。利用先固有の知識、他の配布元の文書、checkpoint、既存の指示やエージェント設定を上書きしない。配置済みの共通文書にローカル編集がある場合は、差分を示して自動上書きを避ける。

ファイルを置くだけでAIへの注入が完了したとは扱わない。必要な文書の検索・選択・読み込みや、指示ファイルへの反映は、各スキルとCLIの利用手順として定義する。

## TypeScriptのまま生成し、mainから配布する

`scripts/build.ts` は `skills/`・`space/` をコピーし、`packaging/` の製品別定義を組み合わせる。TypeScriptからJavaScriptへの変換や、単一バイナリへの変換は行わない。CLIが必要とする `lib/`・資料・依存定義・ロックファイルを含める。

テスト、開発用ファイル、開発リポジトリ自身の `.space/`、すべての `node_modules/` は配布物に含めない。`node_modules/` はGit管理からも除外する。

| 配布先 | 生成するカタログ | カタログが指す配布物 |
| --- | --- | --- |
| Codex | `.agents/plugins/marketplace.json` | `./dist/codex/<plugin-name>` |
| Claude Code | `.claude-plugin/marketplace.json` | `./dist/claude-code/<plugin-name>` |

カタログと配布物の版数はルートの版数からそろえて生成する。ソース・`dist/`・カタログを同じリポジトリの `main` で管理し、ソース変更と生成結果を同じPRに含める。利用者はリポジトリをマーケットプレイスとして登録し、クライアントのインストール・更新機能から配布物を取得する。別のリリースブランチへ生成物を送る構成にはしない。

GitHub Actionsではテスト・型や定義の検証に加え、配布物を再生成してコミット済みの内容と比較する。変更済みファイルだけでなく、新たに生成された未追跡ファイルも確認する。

完成確認では配布物を開発リポジトリの外へコピーし、初回の依存導入、2回目の起動、ロックファイル変更後の再導入を検証する。依存がスキル内に入り、成果物が利用先に保存されること、setupの再実行・更新で重複や既存データの消失が起きないことも確認する。

## 現行実装との差と変更時の判断

2026-09-21の確認時点では `skills/okf-agent-memory/` にOKF CLIがあり、実行時の依存定義はスキル直下の `package.json`、ロックはルートの `bun.lock` にある。`scripts/` 単位の依存管理・bootstrap、タスク用CLI、setup、配布生成・カタログ・CIは、この目標構成に向けた実装・移行事項として扱う。既存CLIまで未実装として扱わない。

作業では、まず変更対象が「配布用ソース」「生成物」「プロジェクト固有の情報」のどれかを確認する。現行コードや配置がこの文書と異なる場合は差分として扱い、現状に合わせて目標を暗黙に変更しない。実装・移行は依頼された範囲で進める。ユーザーから配布先・実行方式・依存配置・正本の責務を変更する指示があった場合は、変更理由と影響を明示し、本文も更新する。

# 共通知識のBabel統合

2026-09-24。[Issue #15](https://github.com/sori883/agent-gear/issues/15)のユーザー依頼により、共通知識・原則の導入先を`.space/babel/vendor/agent-gear/`から`.space/babel/`直下のtype別ディレクトリへ変更する。Codex・Claude Code・Copilotで同じ配置を使い、版数は0.1.2とする。設計正本は[architecture.md](architecture.md)。

## 配置と既存内容の保持

単純なコピー先の変更だけでは、既存のindex.md・log.mdと衝突する。OKFが知識を作成・更新するたびに目次や履歴が変わるため、これらを文書と同じ全体ハッシュで保護すると、通常の知識追加後にsetupを再実行できなくなる。

文書は従来どおりcopyで前回ハッシュと照合する。目次はmerge-indexとし、リンク先ごとに不足する項目を追加する。前回の配布目次をstateのindexSourceへ残し、配布側の項目が変わったときだけ前回・現在・新版を比較する。現在の項目が前回または新版に一致すれば更新・採用し、両側で異なる変更があれば衝突とする。既存の見出し・説明・独自項目を置換しない。初回導入時に存在する同じリンク先の独自表記も保持する。

log.mdとLICENSEはseedとし、存在しないときだけ配置する。共有ファイルの全体ハッシュは、通常更新の編集禁止判定には使わず、pendingの予定内容との照合に使う。これにより途中失敗からの再開でも、適用前・適用後以外の編集を検出できる。

指示テンプレートのBABEL_BUNDLEは利用先のBabelの絶対パスになる。旧VENDOR_BUNDLEの解決と旧vendorのcopyエントリは、旧形式のmanifest・state・pendingを読み取るために保持する。新しい配布manifestはvendorを配置先にしない。OKFが旧vendorを既定検索から除外する挙動は残し、保存した旧コピーが重複検索されることを防ぐ。

## 旧配置からの更新

新版でsetupを再実行すると、共通文書をBabel直下へ配置し、指示の検索先を更新する。旧vendorの文書と管理記録はretainし、自動削除しない。移行対象の旧文書について、同じプラグインの全製品の管理記録と現在内容を照合する。どの記録にも一致しない編集・削除や、未管理の異なる内容は衝突として停止する。新しい配置先に同名の独自文書があっても上書きしない。

旧vendor内の配布元にない独自文書や、目次・履歴のローカル内容を自動移動・統合する処理は含めない。それらは旧配置に保持し、利用者向けsetup資料で確認と統合を案内する。旧版で中断したpendingは旧版で完了させてから更新する。新しいstate形式を書いた後の旧CLIへのダウングレードは対象外とする。

## 検証

配置先を変更したテストで、実装前に18失敗を確認した。setupテストで既存の独自知識・目次・履歴・LICENSEの保持、目次の更新と競合、パス制約、3製品それぞれの旧配置からの更新、製品をまたぐ移行、強制終了後のpending再開を検証する。

配布物を一時ディレクトリへ配置する統合テストで、3製品それぞれについて既存Babelへの導入、OKFの既定検索による23原則の取得、知識追加後のsetup再実行、利用先の依存定義の保持、OKF・orch・setupの起動を検証する。共通原則の孤立文書によるstrict検証不合格は従来からの制約として期待値に残す。

ローカルの最終確認は`bun run test`が169成功・2スキップ・0失敗（990 assertions）、`bun run typecheck`・`bun run build:check`・`git diff --check`が成功。2スキップは比較用Go実行ファイルがないための既存の互換性試験である。生成物は240ファイル。

公開済み0.1.1のGitタグから旧配布物を取り出し、新配布物とともにリポジトリ外で起動した。3製品の新規導入・旧版更新の計6ケースで、既定検索の23原則、知識追加後の再セットアップ、履歴保持、旧vendorの独自文書保持を確認した。全体試験で一度、強制終了テストが書き込みを検出する前に書き手が終了して失敗したため、書き手を起動する前に監視を登録し、終了コード・stdout・stderrも失敗時に報告するようにした。
